## 1. 背景与目标

### 1.1 背景

企业邮箱每天沉淀大量信息：招聘推送、系统通知、告警日报、以及真正需要本人决策与回复的邮件。
人工逐封阅读判断的代价很高，而这些判断本身是高度模式化的——**谁发的（直接还是抄送）、
要不要我回复、截止时间是什么、下一步动作是什么**。

同时，邮件里的时间约定（会议、截止日、上线时间）需要人工再抄一遍到日历，容易漏、容易抄错。

### 1.2 目标

1. **把"读邮件"变成"看结论"**：自动区分「需要你处理」与「需要你关注」，只对前者起草回复。
2. **把"回邮件"变成"审邮件"**：AI 起草、人工逐封确认发送，绝不自动外发。
3. **把"翻邮件"变成"问一句话"**：自然语言检索任意时间范围的邮件，结果可复核、不编造。
4. **把"抄日历"变成"说一句话"**：对话式建日程；把邮件里的时间约定一键转成日程。
5. **换一台电脑就能跑**：零构建、零数据库、双击即用。

### 1.3 非目标（明确不做）

- 不做云端多租户 SaaS，不做团队协作与共享账号。
- 不做自动回复/自动发送：所有外发都必须人工确认。
- 不做邮件正文的全量长期索引：只归档被分析过或被回补拉取过的邮件原文。
- 不代替邮件客户端：不提供写信界面（只审草稿）、不做邮件归档/分类整理。

## 2. 用户与典型场景

**目标用户**：需要长期处理大量企业邮件、且对"误发邮件"零容忍的个人用户（如项目经理、运维负责人）。

| # | 场景 | 期望结果 |
| --- | --- | --- |
| S1 | 早上打开应用 | 一眼看到最近一段时间邮件的结论：几封、几封要我处理、一句话总结 |
| S2 | 某封高优先级直接发给我的邮件 | 点「起草回复」→ 审核正文 → 确认发送 |
| S3 | 再次点击「分析最近 24 小时」 | **不会**为已经发送过的邮件再生成一封待审核草稿；那一行显示「已发送邮件」，点进去看已发送内容 |
| S4 | 抄送给我的高优先级邮件 | 归入「需要你关注」，**不提供起草入口**（回复会越权） |
| S5 | 想知道"苏美佳这个月发过我什么" | 一句话检索，自动回补历史邮件后给出结论与命中清单 |
| S6 | 检索结果里某封邮件想细看 | 点「完整详情」一定打得开：有分析给分析，没有分析给原文摘录 + 「立即分析这一封」 |
| S7 | 邮件里写了"9 月 30 日前提交" | 日历页「从邮件生成日程」→ 确认后写入 Google 日历 |
| S8 | 问"我今天/明天/最近 7 天有什么安排" | 返回统计、冲突提示与文字分析 |
| S9 | 换一台笔记本 | 装好 Node.js，双击 `start.cmd`，浏览器自动打开，填配置即可用 |

## 3. 功能需求

### 3.1 邮件分析（总览）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F1.1 | 一键分析最近 N 小时邮件 | 窗口由配置决定（默认 24 小时），扫描**只读**打开信箱（EXAMINE），不改动任何邮件标记 |
| F1.2 | 逐封分类 | 类型（待处理/询问/会议/通知/订阅/知会/社交通知/垃圾）、优先级（紧急/高/普通/低）、是否需回复、要点、待办、判断依据 |
| F1.3 | 收件人身份判定 | 把每封邮件固化标记为 `direct`（直接发我）/ `cc`（仅抄送我）/ `self`（我自己发的）/ `unknown`，作为后续分流的唯一依据 |
| F1.4 | 分流口径 | **需要你处理** = 直接发我 + 高优先级 + 非垃圾；**需要你关注** = 仅抄送我 + 高优先级。两者互斥，同一封邮件不得同时出现在两处 |
| F1.5 | 统计卡片 | 邮件总数、需你处理、需你关注、待审核草稿（含已发送数）、紧急/高优先 |
| F1.6 | 一句话总结 + 完整简报 | 简报以 Markdown 落盘，可在界面展开 |
| F1.7 | 进度与取消 | 通过 SSE 推送阶段进度（连接/拉取/读正文/会话/分析/起草/简报），可中断 |
| F1.8 | 旧数据兼容 | 升级前的历史记录没有收件人字段，按「直接发我」保守处理，避免丢失待办 |
| F1.9 | **不漏信（硬要求）** | 窗口内命中的邮件必须**一封不漏**地进入分析，不得因协议层的静默丢包而少信：不允许依赖服务端 `ENVELOPE` 的完整性，也不允许依赖服务端 `FROM` 检索。自检要能报出窗口内命中数量，便于与邮件客户端核对 |
| F1.10 | 列表可读性 | 每条列表项都必须能看出「是哪封邮件」：显示主题、发件人、**发件时间**（而非相对时间）与类型标签；任一字段缺失时给出可辨认的兜底（`文件夹 #UID`、未知发件人、分析时间），不得出现空壳行 |
| F1.11 | 类型可辨识 | 8 种邮件类型用**不同颜色 + 图标**区分；列表条目与「邮件构成」图例共用同一套映射，颜色必须能对得上；图标必须是**内联 SVG**（emoji 在小字号下会被系统回退成单色符号，三平台不一致） |
| F1.12 | **数据可下钻** | 统计卡片可点击：数字回答"有多少"，点击回答"在哪里"——定位到对应分区并高亮、跳转到草稿页、或按优先级/类型筛选（可取消）。卡片必须带口径说明 |
| F1.13 | **整行可点看原文** | 邮件列表整行可点击 → 打开详情弹窗，含「AI 分析 / 原始邮件」两个页签；「原始邮件」显示邮件头 + **正文全文** + 引用历史（默认折叠）+ 附件，并提供复制。所有可点行必须**键盘可达**（Enter/Space） |
| F1.14 | **页面状态联动** | 任何会改数据的操作（起草 / 发送 / 删除 / 重写 / 补签名 / 补引文 / 同步草稿箱 / 跑分析 / 改设置）结束后，其他页面的缓存必须失效：在草稿页起草或发送后回到总览，那一行的按钮要立刻变成「查看草稿」/「已发送邮件」。失效不得丢弃阅读位置、对话记录与未保存的编辑内容 |
| F1.15 | **按时间段分析** | 总览页可选分析窗口：最近 24 小时 / 3 天 / 7 天 / 30 天 / 自定义起止（最长 30 天）；标题与分析按钮都跟随该窗口（显示「最近 7 天」而不是「最近 168 小时」）；切换窗口后总览数据必须重取。分析前给出**只读预检**（命中封数、本次取数、已分析过的数量、预计新增分析与模型调用次数、是否截断），窗口较大或预计新增较多时需二次确认 |
| F1.16 | **展示口径必须与所选窗口一致** | 「一句话总结」与「完整简报」只能使用**当前窗口**的简报；当前窗口没有简报时，总结必须由当前窗口的统计现场生成（与卡片同源），并明确告知上一次简报属于哪个窗口。**严禁**把其它窗口的简报当作本期内容展示 |
| F1.17 | **窗口切换的即时反馈** | 点分析按钮后必须**立即**禁用并显示「预检中…」，预检返回后才恢复；确认弹窗必须是**模态**的（可见遮罩、锁页面滚动、Esc 可取消、焦点进入弹窗） |
| F1.18 | **总览头部精简** | 总览页头部只保留「时间范围选择器 + 分析按钮」，两者**必须同一行**（下拉框不得被拉成整行）；不再提供「刷新」按钮——内容更新由数据版本号与 SSE `run:done` 自动驱动 |
| F1.19 | **返回顶部** | 任何标签页滚动超过一屏后，右下角出现悬浮「返回顶部」按钮；点击平滑回到顶部；**切换标签页也要自动复位到顶部**（否则从长列表底部跳过去会停在半空）。无滚动 API 的环境不得抛错 |
| F1.20 | **输入行布局统一** | 「输入框 + 按钮」的行（对话查邮件检索、知识库检索、知识库「问一问」）必须同一行：flex 规则落在**通用的 `.ask-row`** 上，而不是各个容器上——否则新增一处就会漏掉（「问一问」曾经就是这样掉到下一行） |
| F1.21 | **附件清单与按需下载** | 详情「原始邮件」页签必须列出附件名/类型/大小，并可逐个保存到本机。附件从**本地归档**解析（零 IMAP 往返），不支持"服务端写入任意路径"。文件名必须做安全收敛（去路径成分/控制字符/开头点），下载头同时给 ASCII 兜底名与 RFC 5987 的 UTF-8 名。越界或非法序号一律 404，不得取到别的附件 |
| F1.22 | **列表折叠** | 「值得知悉」默认 6 条、「需要你关注」默认 5 条并可展开；「需要你处理」**不得折叠**（待办清单折叠会导致漏看） |
| F1.23 | **日历对话式回顾分析** | 日历知识库内可用自然语言复盘过去一段时间：`过去 7/30 天 / 上个月（自然月）/ 上季度 / 过去一年 / 自定义起止`。**模型只解析意图，不得负责算时间**；区间由服务端按配置时区确定性解析（「上个月」≠「过去 30 天」）。分析必须给出：时间去向、会议负荷与按周趋势、结构性问题、**可执行的优化建议**（含具体动作与量化收益） |
| F1.24 | **回顾口径必须诚实且可复现** | ①统计一律由程序计算（模型只写叙述），保证同一数据同一结论；②日历列表必须**分页取全**，超出上限如实提示"只分析了前 N 条"；③**生活/个人事务不得被排除**（用户记日历的用途正是"标记这段时间被占用"），而应作为独立视角统计；④真正不计入占用的只有四种：已取消、已标记不占忙、我已拒绝、办公地点标注（跨全天），且必须**逐项说明原因与条数**；⑤会议识别走「参会人 + 标题」双通道，并**标注按标题识别的数量**；⑥晚间/周末占用必须**分开统计**会议、独自工作、生活安排；⑦记录稀疏时须明确提示"未记录 ≠ 真实空闲" |
| F1.25 | **回顾结果可导出** | 导出的 Markdown 必须包含：AI 叙述 + **图表**（字符条）+ **统计附录**（口径/总览/按周/生活分类/参与人/问题清单）+ **完整日程清单**，以便离线核对每个数字 |
| F1.26 | **图表输出** | ①应用内图表必须从**接口返回的结构化数据**绘制（本项目的 markdown 渲染器不支持代码块/表格，把图写进 md 在应用内显示不出来）；②SVG 元素必须在 SVG 命名空间、HTML 外壳必须在 HTML 命名空间（用 createElementNS 建 div 不会渲染）；③坐标不得出现 NaN/Infinity；④零数据必须给出说明且**不画柱子**；⑤配色走 CSS 变量以跟随三套主题；⑥**不得使用 `preserveAspectRatio="none"`**（非等比拉伸会把热力图方格压成长方形、柱高失真）；⑦热力图必须用**固定像素尺寸**（其 viewBox 很窄，等比放大后一年份会被拉成数百像素高） |
| F1.26b | **图表布局必须确定** | 布局写死为两列（窄屏单列）+ 宽图跨整行，**不得用 auto-fit 自动排**——自动列数随窗口变化会导致视觉顺序跳动；卡片按内容高度收缩（`align-items:start`）不被同行最高卡片拉长；顺序固定为：按周工作负荷(整行) → 时间构成(整行) → 每日忙碌分布 ｜ 工作主题分布 → 生活花在哪 ｜ 活动时长分布 → 占用时间最多的人(整行) |
| F1.26c | **堆叠条的段内标签必须放得下** | 条高不小于 36；段内标签按**估算文字宽度**（中文 1 字宽、ASCII 0.55 字宽）依次降级为「名称+小时+占比」→「小时+占比」→「占比」→（交给图例），**不得溢出到相邻色块** |
| F1.27 | **导出图表必须通用** | 导出文件里的图表用字符条（`█`/`░`）绘制：**数字放在条之前**（字体不等宽导致错位时仍可读）、**不使用代码围栏**（纯文本查看器里不会出现反引号）；文件保持自包含，可在记事本/邮件正文/GitHub/Obsidian 中阅读 |
| F1.28 | **人名归属** | 除参会人字段外，必须支持**从标题解析人名**（「与X、Y讨论Z」），并标注来源；解析规则保守优先（宁可少识别，也不要把"和老婆孩子过纪念日"当工作对象）。用于产出「时间被谁占用最多」 |
| F1.29 | **时长分层与地点** | 按时长分 4 档（<30min / 30–60 / 1–2h / >2h）；地点分线上/线下/**未填**（没填地点不得猜成线下） |
| F1.30 | **两个视角必须分清** | 「总占用」= 工作 + 生活（回答"我的时间被占了多少"）；「工作负荷」= 会议 + 独自工作 + 专注（**不含生活**，回答"工作有多重"）。生活事务必须：计入总占用与日程清单、有独立的生活子类统计（运动健身/家庭陪伴/餐饮/医疗健康/个人事务/休闲娱乐/休息/其他）、出现在图表与报告叙述中。**不得出现"口径为纯工作"这类把生活略过的表述** |
| F1.31 | **休假按天计** | 休假/外出不计入小时口径（一条"年假 48 小时"会把所有数字压平），只按天统计；但仍计入占用条目与日程清单 |
| F1.32 | **跨天事件不得重复计数** | 跨天事件会按天拆进各天的 bucket（便于按天展示），但**去重键必须用原始开始时间**，否则一条 3 天出差会被算成 3 条晚间/周末占用 |
| F1.33 | **图表版式与热力图行标签** | 版式固定：按周工作负荷(整行) → 时间构成(整行) → 中间一行（左列**一个容器装上下两张**、中列主题、右列热力图）→ 人名榜(整行)。左列必须是容器而非两个网格行，否则两张之间会被中列撑出空隙；中列与右列须与左列**等高**。热力图每行左侧必须标出**该周日期范围**（如 `9.28~10.4`），格子右移让出标签栏；首末行只显示实际覆盖到的日期 |
| F1.34 | **图表配色必须能分辨** | 会议=主色、独自工作=**橘**、生活/个人=**紫**、专注块=青；三套主题下四色**互不相同**且"独自工作"为橘色系、"生活/个人"为紫色系（要有测试守住，避免改回撞色） |
| F1.35 | **界面一致性** | ①块头(`.block-head`)、检索区(`.search-panel`)、块内正文(`.pad`) 的左右内边距必须统一为 16px——`​.pad` 曾是 4px，导致**全站**"块头标题 → 正文第一段"错开 12px；②视图层**不得使用内联 `style`**（魔法数字是页面之间慢慢走形的根源），间距统一走 4/8/12/16 四档工具类（`.mt-1/2/3/4`、`.mb-3`）与语义类（`.block-lead`/`.block-note`/`.block-body`/`.flush-head`）；③工具类必须真实存在（否则替换后静默失效） |
| F1.36 | **横向条形图用 HTML 固定几何** | Top 榜类图表（活动时长分布/生活花在哪/工作主题分布/人名榜）必须用 **HTML 行**而不是 SVG：SVG 的条高与行距是画布坐标，会随卡片宽度等比缩放，导致"同为 1.3fr 与 1fr 的两列，柱子高矮与疏密不一致"（用户实测）。改用 CSS 后行高、条高、行距、字号都是**绝对像素**，与卡片宽度无关；标签列宽固定，不同卡片的柱子起点也对齐。唯一的动态值是填充宽度百分比 |
| F1.37 | **块头操作区不得被挤到下一行** | `.head-actions` 必须 `flex: 0 0 auto`（不收缩），按钮加 `.nowrap`；块头标题可省略（`min-width:0` + ellipsis）以让出空间。长文字（如"扫描窗口：…"）**不得放进 `.head-actions`**——它会把按钮顶到标题下面（用户实测） |
| F1.38 | **同一页上的数字必须能对上（关键）** | 用户实测：简报写「近 24 小时共 11 封邮件，2 封高优先级需尽快处理」，同一页卡片却是「邮件总数 5 / 需你处理 0」。三处根因都必须消除：①**拉取窗口比宣称的宽**——IMAP `SEARCH SINCE` 只精确到「天」，所以"最近 24 小时"会多带回当天更早的邮件（实测 11 封里 6 封距当时 24–43 小时）→ 拉取后必须**按精确时刻再滤一道**（时间解析不出的保留；`scope` 点名重析不过滤）；②**简报写的是"本次拉取数"**，卡片写的是"严格窗口内数" → 简报输入必须写清「窗口内共 N 封」，并声明统计是**程序算出的事实、引用时必须原样**；③**简报是那次分析的快照，卡片是打开页面时实时算的** → 简报须带上当时的 `snapshot` 与当前 `live` 计数，两者不同时界面要**主动说明"数字不同是因为时间在走"**，而不是让用户怀疑算错了 |
| F1.39 | **模型不得自造与卡片冲突的数量** | 输入里已明确"需回复 0 封"，模型仍写出"2 封高优先级需尽快处理"（用户实测）。提示词必须约束：数字只能原样引用、**不得自行加减或改写**；「需要你处理」一节**需回复为 0 时只能写「无」**，不得用会议通知/到期提醒来填充；不需回复但有明确时限的事放进「值得知悉」 |
| F1.40 | **花钱前的估算必须与真实运行一致（关键）** | 预检曾按"已分析比例"估算复用率，写着"其中 N 封已分析过，**不会重复消耗**"，而分类阶段其实对窗口内**全部**邮件都会重跑（实测连续 6 轮都是 拉取 11 → 分析 11）——等于拿错数字劝用户花钱。①预检必须算出**真实**的复用集合（`已有分析 且 已有草稿`），`estimatedAnalyze = taken - reusable`；②文案如实说明只有"已有草稿"的才复用；③**真正实现该复用**：已有草稿的邮件直接复用已有结论，不再调用模型（省 token），并用 `result.reused` 如实报告。复用条件刻意收得很紧：全量复用会让分类提示词演进（如新增 `worthNoting`）后老邮件永远拿不到新字段；用户删掉草稿即自愈。④复用记录**必须带上本轮的 folder/uid/messageId**——漏了会让下游 `upsertAnalyses` 静默跳过（邮件从清单消失），并让起草去重键变成 `undefined:undefined`（已发送的邮件被重新起草） |

### 3.2 邮件草稿与发送
| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F2.1 | 自动起草 | 只对「需要你处理」的邮件起草，受 `maxDrafts` 上限约束 |
| F2.2 | **不重复起草（关键）** | 已经有草稿的邮件（无论待审核还是已发送）**不再重新起草**。原因：草稿 id 由「文件夹 + UID」推导，重新起草会覆盖用户已修改的正文；对已发送的邮件更会把它"降级"回待审核，诱导重复发送、并抹掉发送时间等审计信息 |
| F2.3 | 状态语义 | 总览里每行按草稿真实状态显示动作：**已发送 → 「已发送邮件」**（跳到草稿页的「已发送」标签并选中该封）；待审核/失败 → 「查看草稿」；无草稿 → 「起草回复」 |
| F2.4 | 草稿编辑 | 改收件人/抄送/主题/正文；「让 AI 重写」可带一句要求 |
| F2.5 | 人工确认发送 | 必须弹确认框（展示收件人/主题/正文）并携带 `confirm=true`；后端在缺少确认时返回 428 |
| F2.6 | 发送幂等 | 已发送的草稿不可再次发送、不可修改、不可重新起草 |
| F2.7 | 草稿箱同步 | 可把草稿以 `\Draft` 追加到服务器草稿箱；发送后按配置清理副本、可选归档到「已发送」 |
| F2.8 | 签名 | 多行签名由程序逐字追加，幂等（不重复出现）；可为存量草稿一键补签名，**不动已发送的草稿** |
| F2.9 | 发送后告知 | 如实列出发送后处理结果（已清理服务器草稿、已删除旧副本、已归档到某文件夹、某项失败） |
| F2.10 | **回复带原始邮件引文** | 回复正文顺序必须是「新正文 → 签名 → 引文」；引文只取来信的"新内容"（不重复引用引用历史）；提供**中文客户端风格**（`------------------ 原始邮件 ------------------` + 发件人/发送时间/收件人/抄送/主题）与 **`>` 前缀风格**两种，设置里可切换、可关闭、可设字数上限；同一封的引文**幂等**（不出现两份） |
| F2.11 | 存量草稿可补引文 | 对已有且未发送的草稿提供「插入原文」一键补（不静默改写、不动已发送的草稿），正文变更后把草稿箱副本标记为过期 |
| F2.12 | 草稿箱副本不留孤儿 | 重复「同步到草稿箱」必须先清理上一份副本；仅在该服务器支持 `UIDPLUS` 时做 `UID EXPUNGE`，否则退回只打 `\Deleted` 标记（**绝不**用裸 `EXPUNGE`，以免误删用户在客户端标记的其它邮件） |
| F2.13 | 标签计数 | 草稿页「待审核 / 已发送 / 全部」都要显示数量，且数量是**全量口径**（切标签时不互相归零） |
| F2.14 | 发送后落点明确 | 发送成功后给出「查看已发送」入口，避免草稿从待审核列表消失后用户误以为出错 |
| F2.15 | **签名位置规则** | 正文顺序固定为「新正文 → 签名 → 引文」，签名必须位于**引文之上**；「有没有签名」必须是「包含且位置正确」的语义，**不得**用「以签名结尾」判断（引文会在签名之后）。位置不正确时必须可检出、可一键搬回，且搬移后签名只出现一次 |
| F2.16 | **发送时间的时区** | 生成的 MIME `Date:` 头必须按 `calendar.timeZone` 写成带数字偏移的形式（如 `+0800`），不得写 `GMT`；IMAP `APPEND` 的 internal date 与本地 `sentAt` 必须是同一时刻 |
| F2.17 | 草稿页分析入口 | 草稿页保留「继续分析新邮件」（与总览同一个分析入口），跑完必须**自动刷新列表**并提示新增/跳过的封数，不得要求用户手动刷新页面 |
| F2.18 | **草稿附件发送** | 可给草稿添加/移除多个附件（选择或拖拽），发送时报文必须是 `multipart/mixed`（正文作为内层 alternative，不得因层级变深而丢失正文）。发送前按 **base64 编码后**体积校验，超限必须**在界面禁用发送并在后端拒绝**（413），不得等 SMTP 报错。确认框逐项列出附件名与大小 |
| F2.19 | **附件生命周期** | 附件内容落在 `data/attachments/`（state.json 只存元数据与文件名，**不存绝对路径**，以便整体搬迁）；删除草稿时一并清理文件；发送成功后清理内容但保留元数据；已发送的草稿不得再增删附件（409） |

### 3.5 日历数字人（Google Calendar）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F5.1 | 对话建日程 | 自然语言 → 日程草稿（标题/起止/参与人/地点/提醒）→ **人工确认后**才写入 |
| F5.2 | 信息不足则追问 | 缺标题或缺时间时追问，不瞎编 |
| F5.3 | 时区纪律 | 模型只输出"本地墙上时间"字符串，服务端按 `calendar.timeZone` 解释成真实瞬间；相对表达（今天/明天/下周五）由模型结合给定的当前时间上下文解析 |
| F5.4 | 邮件转日程 | 从已分析邮件里提取时间线索（会议、截止日）→ 给出建议列表 → 逐条确认后写入，并带上来源邮件标记 |
| F5.5 | 日程分析 | 今日 / 明日 / 最近 7 天的统计、冲突提示与文字分析 |
| F5.6 | 会话保留 | 切走再切回页面不丢对话记录与待确认日程；**不自动重新拉取**，只有用户点「刷新日历」才刷新 |
| F5.7 | 不重试写操作 | 创建日程的 POST 不重试（重试会产生重复日程）；DELETE/PATCH 仅在连接根本没建立时重试 |
| F5.8 | 错误可执行 | Google API 未启用 → 给出启用链接；账号未在测试用户列表 → 给出授权指引（含"未经 Google 验证"警告页该点哪个按钮） |
| F5.9 | **网络出口可配代理** | 程序必须支持为 Google 访问配置 HTTP 代理（界面 + 环境变量），且**只影响 Google**，不动邮件与大模型链路；代理必须真正生效（含 `CONNECT` 隧道、代理认证、`NO_PROXY`），而不是只把地址存下来 |
| F5.10 | **网络故障可定位** | 连不上 Google 时必须给出**底层错误码**（ENOTFOUND / ETIMEDOUT / ECONNRESET / 407…）与中文原因、以及"下一步该改哪里"，不允许只显示 `fetch failed`；自检里要有独立的「Google 网络出口」项，把"网络不通"与"凭据/权限问题"分开 |
| F5.11 | **产生日程的入口集中** | 「从邮件生成日程」必须紧跟「对话建日程」放在**同一栏**，不得分散到另一栏底部（两个"产生日程"的入口应在一处）；待确认卡片仍紧跟对话区——它本身就是对话的确认步骤 |
| F5.12 | **写入日历前可修改** | 邮件生成的每条建议必须支持**写入前编辑**：可改主题、全天/起止时间、地点、说明，改动作为 `override` 传给后端；同时保留「直接写入」快速路径。弹窗须显示来源邮件与原话依据。只给部分字段时其余沿用原建议；改过内容**仍须保留来源标记**（`mailbotSource=email`、`mailbotRef`），否则"由邮件生成"的溯源会断 |
| F5.13 | **扫描窗口必须与文案一致（关键）** | 按钮写「扫描最近 24 小时邮件」，就必须真按 **24 小时**过滤（按**邮件日期**，即 `mail.date`），不得退化成"分析库里最新的若干封"。窗口大小须可由调用方指定，且响应里回传 `window.hours / window.since / window.sinceLabel` 供界面显示核对 |
| F5.14 | **窗口为空时自动补一次分析** | 窗口内没有可用邮件时（且调用方未点名 `ids`），必须**自动先跑一次 24 小时邮件分析**（`runScan`，其自身跳过已分析邮件，不重复花 token）再重新提取，让"扫描最近 24 小时邮件"一步到位。自动分析的结果（`fetched` / `analyzed`）须回传并在界面说明，避免用户以为卡住。**自动分析失败不得让接口不可用**：应如实返回失败原因，仍然给出空建议与提示 |
| F5.15 | **抽到的时间要规整成可用的时间块** | 邮件里抽出的往往是"时间点"而非日程（实测出现 17:00→17:05、10:52:12→10:52:17 这类 5 分钟条目）。必须规整：①开始对齐到**整点或半点**；②**截止类（deadline）向下取整**（"10:52 之后无法登录" → 10:30），保证提醒不晚于邮件里说的时间；其余就近取整；③时长不足 30 分钟的补足 30 分钟，**模型已识别出更长时长则保留**；④全天事项不受影响；⑤规整过就要在响应里标记（`timeAdjusted`）并在界面说明，让用户知道时间被程序调整过 |
| F5.16 | **代理路径禁用 `agent: false`（关键缺陷）** | Node 在 `agent: false` 时会新建一次性 Agent 并**忽略 `createConnection`**，导致 CONNECT 隧道 socket 被丢弃、程序直连目标 —— 表现为"日志显示隧道已建立，却 ECONNRESET/超时"。代理路径必须**不传 `agent`**（或不传 `agent: false`）以让 `createConnection` 生效；代码里须留注释说明，防止后人加回 |
| F5.17 | **已有日程必须可修改** | 接通 `google-api.js` 里早已写好却**从未被调用**的 `updateEvent`：每个日程提供「编辑」（改标题/时间/地点/说明），走 `PATCH /api/calendar/events/:id`。①只发 PATCH，未提供的字段（**参会人、扩展属性**）必须保持不动——否则"这条是哪封邮件来的"会丢；②**手动改的时间不得套用整点/半点规整**（规整只针对邮件抽出的时间点）；③"结束早于开始"必须**明确报错**，不能像邮件抽取那样悄悄按默认时长兜底；④改动须进操作台账并记录改了哪些字段；⑤「编辑」与「删除」并列，不得因为新增编辑而丢掉删除 |

| F5.18 | **授权失效必须被识别并如实呈现（关键）** | `refresh_token` 会失效：同意屏幕处于「测试」发布状态时 Google 只给它 **7 天**寿命，用户也可能在账号里撤销。①**连接状态不得只看"文件里有没有 token"**——那样界面会一边显示「已连接」一边每个请求都失败；②刷新返回 `invalid_grant` 时必须**把失效状态落盘**（`revokedAt`/`lastRefreshError`），据此把 `connected` 置 false 并给出 `needsReauth`；③已知失效后**快速失败**，不再去撞注定失败的刷新；④文案必须说明**最可能的原因与免去周期的方法**（把发布状态改为「已发布」），而不是只说"授权已被撤销"；⑤重新授权成功后必须**清掉失效标记**；⑥**报错页必须真的给出「重新连接」按钮**——旧文案写着"请重新点击「连接 Google 日历」"，而报错页只有「重试」，属于文案承诺了页面上不存在的动作 |

### 3.8 运行与记录（操作审计）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F8.1 | **写外部系统的动作必须留台账** | 控制台日志关窗即失，而以下操作改了外部状态，必须持久记录：**创建日程、删除日程、发送回复邮件、同步草稿到邮箱、删除草稿**。每条含：时间、动作、**具体标题/主题**、来源（对话建日程/从邮件生成/界面操作）、结果（成功/失败+原因），以及可查性所需的细节（收件人、时间、附件名、来源邮件主题、文件夹） |
| F8.2 | **台账只追加、不改写、永久保留** | 存 `data/audit.jsonl`（一行一条 JSON），**不放进 `state.json`**——后者每次变更都要整体重写解析，台账是只增不改的，混在一起会拖慢每次状态保存。永久保留（用户选择），因此界面须支持筛选与「下载 JSONL」，而不是把整个文件塞进页面 |
| F8.3 | **审计失败绝不影响主流程** | `appendAudit` 必须捕获所有异常并返回 `null`（发信/建日程已经完成，不能因为记不上台账就让用户看到失败）；读取时跳过写坏的行，不让一行毁掉整个列表 |
| F8.4 | **台账可按类别 / 动作 / 关键词 / 只看失败筛选** | 关键词必须能搜到**目标、动作名、来源、错误信息，以及 extra 里的收件人/附件名/来源邮件主题**（"这封信发给谁了""这个附件发出去没有"是最常见的追问）。读取须**从文件尾部往前扫**并在够数后停止，避免大文件全量解析；被 limit 截断时须回传 `truncated` 与命中总数 |
| F8.5 | **运行历史要有界面** | `state.json` 的 `runs`（最近 100 条）与 `GET /api/runs` 早已存在却没有界面。运行与记录页须展示最近 30 次（拉取/分析/需回复/草稿数、成败、耗时、失败原因） |
| F8.6 | **筛选必须真的重新取数** | 筛选条件变化后的加载**必须强制重取**——否则会被"已加载过"的视图缓存挡掉，表现为"点了筛选没反应" |
| F8.7 | **空台账不得下载出空文件（关键）** | 没有记录（文件不存在或为 0 字节）时，`/api/audit/download` 必须返回 **404 + 明确原因与下一步**，而不是 200 + 空 body——后者会让浏览器下载一个 **0 字节文件**，用户打开是空的、只会以为功能坏了（用户实测踩到）。界面在空态下必须**禁用下载**而不是给出链接 |
| F8.8 | **历史操作必须可补录** | 台账是本功能上线后才开始记的，此前的操作必须能回填，且**只读外部、只追加本地**、可重复执行。两个来源缺一不可：①**本地日历会话记录**（「已写入日历：标题　时间」消息）覆盖"对话建日程"；②**Google 事件上的 `mailbotSource`/`mailbotRef`** 覆盖"从邮件生成"。补录时间用当时的创建时间（会话消息时间 / 事件 `created`），不得用"补录这一刻"；按（标题+时间）或日程 id **去重**；标题含全角空格时不得被误切 |
| F8.9 | **创建日程必须打来源标记** | **所有**创建路径都必须写 `mailbotSource`，包括**对话建日程**——旧实现只有"从邮件生成"会写，导致 107 条日程里仅 3 条可识别（用户实测），既无法在 Google 侧区分，也让补录漏掉整批历史 |
| F8.10 | **补录不得被网络拖死（关键）** | 补录的两个来源必须**先本地、后 Google**：本地会话记录瞬时完成且**不依赖网络**，Google 那一路只是"尽力而为"。①Google 查询必须有**超时上限**（默认 20s）；②超时或失败**不得丢掉已完成的本地结果**，须保留并在响应里带上失败原因（`calendar.error`）；③前端须有**兜底超时**（40s）与明确文案，绝不允许出现"点了没反应、按钮一直显示补录中…"（用户实测踩到）；④Google 侧失败时提示须说明"本地已补 X 条，Google 那一路未成功 + 原因"，不能报成整体失败 |

### 3.9 待办闭环

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F9.1 | **「需要你处理」必须能清空** | 没有状态时，每次分析都会把**已经处理过的邮件再列一遍**，清单永远清不空 —— 那就只是一份报告，不是一个待办系统。每条必须可标记：**已处理 / 稍后提醒 / 忽略**，并可恢复为待办 |
| F9.2 | **状态存本地且与邮件一一对应** | 状态键必须与 `analysisKey` 一致（`folder:uid`），不在任务里重复存邮件信息（否则会出现"任务与邮件对不上号"）。存于 `state.tasks`，**不进操作台账**——台账只记"改了外部系统"的动作，掺进本地点击会让它失去意义 |
| F9.3 | **稍后提醒到期必须自动回来** | `snoozed` 在 `snoozeUntil` 之前隐藏，**到点自动回到清单**；`snoozeUntil` 非法/缺失也一律当作"回到清单"，绝不能因为一个坏时间让邮件永远出不来 |
| F9.4 | **徽标与统计只计未处理** | `stats.needsReply` 必须只数 `open` 的（含已到期的稍后提醒），这样徽标是**可清零**的；已处理/稍后/忽略的数量另用 `taskDone/taskSnoozed/taskIgnored` 给出 |
| F9.5 | **已闭环的必须能翻回去** | 总览提供「已经不在清单里（已处理/稍后提醒/已忽略）」分组，**默认折叠**（不该占首页重点位置，但不能消失），展开后每条可**恢复为待办**；稍后提醒要显示"提醒时间"、已处理显示"处理时间"、有备注显示备注 |
| F9.6 | **回到 open 要删记录** | 恢复为待办等于"没做任何标记"，应删除状态记录而不是留一条 `open`——否则"点了一下又撤销"也会让 `state.json` 无限增长 |
| F9.7 | **不留孤儿状态** | 分析记录被容量收敛掉之后，针对它的任务标记必须一并清理（否则状态文件只增不减） |
| F9.8 | **稍后提醒给常用档位** | 提供"今天下午 14:00 / 今天 18:00 / 明天早上 09:00 / 3 天后 / 下周一"等档位，而不是只让用户填时间：绝大多数"稍后"就是"下午再看"，少一次输入就少一次放弃使用 |

### 3.10 需留意（不需回复但有明确时限）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F11.1 | **「需留意」必须单列一类** | 有些邮件**不需要回复**却有明确时限或要你亲自去办（到期提醒、待确认参会的会议、待补交材料）。塞进「需要你处理」会把那份"要你回信"的清单灌满；塞进「值得知悉」又会被"看看就好"的内容淹掉——而这恰恰是"别错过"的东西 |
| F11.2 | **判定权交给逐封分类，本地只做收敛** | **不得**用"有 actions 就算"这类本地启发式：实测模型几乎给**每一封**都填了 actions（连日用电费账单都有"按需查看并缴纳"），那样「需留意」会变成第二个收件箱。分类提示词新增 `worthNoting` 字段（口径是"**不去办会误事**"，拿不准填 false），本地只收敛：垃圾/纯知会不进、低优先级不进、**需要回复的不进**（与「需要你处理」互斥，避免同一封出现两次） |
| F11.3 | **老记录不改变行为** | `worthNoting` 是新增字段，历史分析记录没有 → 一律视为 false（不做启发式回填，行为可预测）；重新分析一次即可补齐。降级记录（模型失败）也必须有该字段，保持记录形状一致 |
| F11.4 | **「需留意」也要能清空** | 与「需要你处理」共用同一套待办状态（已处理/稍后提醒/忽略，可恢复），**但不提供「起草回复」**——这类邮件本就不需要回复，摆一个起草按钮只会诱导用户去回一封不必回的邮件。已闭环分组必须**覆盖两类清单**，否则从「需留意」标记掉的条目就再也找不回来了 |
| F11.5 | **徽标口径独立** | 「需留意」自己一个计数（`stats.worthNoting`），**不并入**「需要你处理」；导航徽标仍只数需要处理的，避免"要你回信"的紧急度被稀释 |

### 3.11 存储与清理（数据保留）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F12.1 | **"清理"必须区分结论与原文** | 结论（摘要/待办/统计/简报/台账）在 `state.json` / `reports` / `audit.jsonl` 里；`data/raw/*.eml` 只是**原文归档**，只影响「查看原文 / 下载附件 / 重新起草」。清理界面必须把这条讲清楚，不能让用户以为"清原文字符=清历史" |
| F12.2 | **孤儿清理必须零风险** | 分析记录被容量收敛后，对应的 `.eml` 会变成**没有任何界面入口**能访问的孤儿文件（`persistState` 的收敛只删 state 条目，从不动原文）。删除这些文件**不损失任何可查询的历史**，应作为默认、可一键执行的清理项 |
| F12.3 | **按保留期清理必须显式确认且说明代价** | 删除"有主"的原文会牺牲离线可用性：邮件还在服务器上时程序会回连邮箱重取（`loadRawFor` 有兜底），**邮件已删除或超出服务器保留期时就彻底查不到**。因此：默认保留天数为 **0（永久保留）**、必须用户主动设置并二次确认、且**只动 `data/raw/*.eml`** |
| F12.4 | **清理是不可逆的数据损失，必须进台账** | 与"点一下待办"不同，删原文是永久损失——事后必须能回答"我的邮件原文是什么时候没的"。故新增 `storage.cleanup` 审计动作（含孤儿数、超期数、释放字节、清理前占用） |
| F12.5 | **占用要看得见** | 提供 `GET /api/storage`：原文/孤儿/简报/台账/状态的**文件数与字节数**，以及分析记录数与当前保留策略。此前用户完全看不到 `data/raw` 已经涨到 160 MB |
| F12.6 | **分析记录上限必须可配置** | 旧版本写死 `MAX_ANALYSES = 3000`，超限**静默**删最旧的——用户既不知道也没法调。改为 `retention.maxAnalyses`（默认 3000），并在设置页说明"调小会让旧邮件从列表/统计/搜索里消失" |

### 3.12 持续集成（交付前提）
| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F13.1 | **CI 必须能无凭据运行** | 测试全部离线（mock IMAP/SMTP/LLM/Google + 临时数据目录），因此 CI 不需要邮箱授权码、不需要 Google 令牌、不花 token——这是上 CI 的前提，任何"需要真实凭据才能跑"的测试都不许进入 `npm test` |
| F13.2 | **跨平台矩阵** | 本项目主要在 Windows 开发，但路径分隔符/大小写/换行符问题只有跨平台才暴露：矩阵为 Windows + Ubuntu × Node 20/22；并用 `.gitattributes` 统一 LF（`*.cmd` 保留 CRLF，否则 cmd 解析会坏） |
| F13.3 | **CI 必须有一道防泄漏闸门** | 一旦有 `data/`、`.env`、令牌、`.eml`、`audit.jsonl` 被提交就**直接失败**。`.gitignore` 曾逐文件列举而漏掉 `data/google-token.json`（活的 OAuth 令牌）、`data/audit.jsonl`（真实人名与日程标题）与 `data/attachments/`；现改为整目录排除，并在 CI 上再拦一道——比事后重写历史便宜得多 |
| F13.4 | **公开仓库前必须脱敏** | 文档与测试夹具里可能带着**真实公司域名、工作邮箱、姓名、手机号**。首次公开前必须全量扫描并替换为通用示例（脱敏后夹具与断言仍自洽），否则一旦推上公开仓库，这些隐私就随历史永久留存 |
| F13.5 | **时区参数不得省略，且必须有"进程时区 ≠ 配置时区"的 CI 守卫（关键）** | 所有时区相关函数（`partsInZone`/`formatInZone`/`dayKey`/`addDays`/`localDateString`…）**必须显式收到配置时区**；一旦漏传，`Intl` 会**静默回退到进程本地时区**——本机时区恰好等于配置时区时永远测不出来，换机器/CI 上就静默算错一天。**真实案例**：`localDateString(addDays(d, 1, tz))` 的 `timeZone` 只传给了内层 `addDays`，外层 `localDateString` 没收到 → Ubuntu（UTC）上"全天事件结束日"算成与开始日同一天，而 Windows 本地（+08）一直通过。因此：①函数内保留兜底（缺失时用**配置时区**，绝不落到进程时区）；②`presentEvent` 的兜底链同样补上配置时区；③CI 矩阵必须含一个**与配置时区不同**的进程时区（用负偏移 `America/New_York`，Ubuntu 默认的 UTC 覆盖不到镜像情形） |

### 3.13 定时分析与通知（主动性）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| F10.1 | **必须能自己动起来，且默认关闭** | 在此之前程序只有被点击才动作。定时分析在设定时刻自动拉取并分析。**默认必须关闭**：它会在用户不知情时连邮箱、消耗大模型额度、把正文送模型，这种"替你做事"的能力必须由用户明确开启 |
| F10.2 | **到点判定必须是可测的纯函数** | 触发判断（是否开启/是否到点/星期是否允许/是否已在跑/本时刻是否已跑过）必须抽成不依赖时钟的纯函数，直接测四种情况，而不是靠等真实的分钟边界 |
| F10.3 | **同一时刻只跑一次** | 用 `lastSlot`（配置时区的 `YYYY-MM-DD HH:MM`）作幂等键：进程重启、tick 抖动、手动改系统时间都不得重复触发 |
| F10.4 | **不得与手动分析并发** | 引擎已有任务在跑时必须跳过本次（不能去撞出 `RUN_IN_PROGRESS`，更不能把那句报错写进 `lastError` 并白占一个时刻） |
| F10.5 | **失败也要占住这个时刻** | 失败必须记 `lastError` 并**同样占用 `lastSlot`**，否则"邮箱连不上"会变成每分钟重试一次，把日志与网络刷爆 |
| F10.6 | **只在确实有事时打扰** | 通知前先判断有无待办或新草稿；没有就只记日志不打扰。**三种渠道各自独立**：①页内提示（SSE `notify` → 弹条，`notify.inApp`）；②浏览器桌面通知（需页面开着并授权，`notify.browser`，打开开关时**立即申请权限**）；③**自寄简报**（`notify.email`，唯一在用户什么都没打开时也能收到的渠道） |
| F10.7 | **通知失败不得影响分析结果** | 自寄简报失败只记 warn，分析结果与台账照常；定时分析的通知入口同理，绝不因为"发不出提醒"而让整次分析算失败 |
| F10.8 | **开关保存后立即生效** | 保存配置后定时器必须**立即起停**，不必重启服务（否则用户会以为没生效又去点一次）；设置页须显示**实时状态**：定时器是否在跑、上次执行时间与结果、上次失败原因，并给「立即试一次」（不受时刻限制，用来确认邮箱与大模型都通） |

## 4. 非功能需求

### 4.1 安全（最高优先级）

| 编号 | 要求 |
| --- | --- |
| N1 | **不自动外发**：任何邮件发送都必须经过界面确认并携带 `confirm=true`；默认策略为 `confirm` |
| N2 | **不自动写日历**：写入日程必须 `confirm=true` |
| N3 | **扫描只读**：信箱以 EXAMINE 打开，不把未读变已读、不改动标记 |
| N4 | **提示词注入防护**：邮件正文被当作数据而非指令；系统提示中明确禁止执行邮件里的指令 |
| N5 | **同源与令牌**：签名授权 URL 只接受回环地址；写操作与凭据接口拒绝跨源请求；可配置本地访问令牌 |
| N6 | **密钥不回显**：配置接口一律脱敏；掩码值不会覆盖磁盘上的真实密钥 |
| N7 | **本地闭环**：除 IMAP/SMTP/大模型/Google 之外不向外发送任何数据；数据目录不出本机 |

### 4.2 可移植与可维护

## 5. 数据与口径

### 5.1 关键数据对象

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| 实例 instance | id / label / imap / smtp / identity | 一个邮箱一套独立配置 |
| 分析记录 analysis | key(`folder:uid`) / type / priority / needsReply / summary / actions / reason / recipientKind / mail / context | 每封邮件一条，重复分析覆盖 |
| 草稿 draft | id(`draft_<folder>_<uid>`) / status / to / cc / subject / body / source / mailbox / sentAt / sendResult | id 由邮件推导，天然幂等 |
| 简报 report | id / file / meta | Markdown 落盘 |
| 日程会话 session | id / messages / pendingEvents | 日历对话上下文 |

### 5.2 分流口径（唯一权威定义）

```
需要你处理  = recipientKind == 'direct' 且 priority ∈ {urgent, high} 且 type != 'spam'
需要你关注  = recipientKind == 'cc'     且 priority ∈ {urgent, high} 且 type != 'spam'
起草队列    = 需要你处理 中「还没有草稿」的邮件（受 maxDrafts 上限）
```

- 同时出现在 To 与 Cc 时，按「直接发我」处理。
- 历史记录（无 `recipientKind`）按「直接发我」保守处理，避免丢待办；重新分析后即按新口径分流。
- 只保留**高优先级**进入这两个列表，低优先级不占用首页注意力。

### 5.3 草稿状态机

```
（无草稿）--起草--> pending --确认发送--> sending --成功--> sent
                        |                    |
                        |                    +--失败--> failed --保存/重写--> pending
                        +--删除--> （无草稿，可被重新起草）
sent：终态，不可修改/重发/重新起草；重新分析也不会把它变回 pending
```
