## 1. 环境要求

| 项目 | 要求 |
| --- | --- |
| Node.js | **20 或更高**（推荐 22 LTS）。`node -v` 可查看 |
| 操作系统 | Windows 10/11、macOS、Linux 均可 |
| 浏览器 | Chrome / Edge / Firefox 等现代浏览器 |
| 网络 | 能访问你的企业邮箱 IMAP/SMTP；能访问大模型 API（默认 DeepSeek）；使用日历需能访问 Google |
| 磁盘 | 约 100MB（含依赖）；原文归档按邮件量增长，通常每月几十 MB |
| 不需要 | 数据库、Docker、构建工具链、公网 IP |

安装 Node.js：

- Windows / macOS：到 <https://nodejs.org/zh-cn/download> 下载 LTS 安装包，一路默认即可（会自动加入 PATH）。
- Linux：`sudo apt install nodejs npm` 或使用 nvm。

安装完成后**新开一个终端**执行 `node -v` 验证。

## 2. 一键启动（推荐）

### Windows

1. 把整个项目文件夹复制到本机（例如 `D:\mailbot`）。
2. **双击 `start.cmd`**。

脚本会自动完成：

| 步骤 | 动作 |
| --- | --- |
| 1 | 检查 Node.js 是否存在、版本是否 ≥ 20 |
| 2 | 若 `node_modules` 不存在则执行 `npm install`（首次约 1-2 分钟，需联网） |
| 3 | 若 `.env` 不存在则从 `.env.example` 复制一份 |
| 4 | 启动服务并**自动打开浏览器**（带访问令牌的完整地址） |

> 关闭那个命令行窗口即停止服务。
>
> **`start.cmd` 只做三件事**：`cd` 到脚本所在目录、确认 `node` 存在、把 `node cli.js start` 叫起来。
> 所有检查与中文提示都在 Node 侧（`server/lib/startup.js`），所以三个平台行为一致，也不会因编码问题出错。
> 这个文件必须保持**纯 ASCII + CRLF 换行**：cmd.exe 解析含中文（UTF-8）的批处理时会在多字节字符之后
> 错位，把后续行的行首字符吃掉（`call`→`all`、`echo` 消失、`node cli.js serve`→`serve`），
> 满屏报 `'xxx' is not recognized as an internal or external command`。测试里有专门用例守住这两点。

### macOS / Linux

```bash
chmod +x start.sh
./start.sh
```

### 也可以用命令行 / npm 脚本

```bash
node cli.js start            # 等价于双击 start.cmd（检查环境 → 装依赖 → 起服务 → 开浏览器）
node cli.js start --check    # 只做启动前检查、不启动服务（排查环境问题时用）
node cli.js start --port 8899 --no-open   # 换端口、不自动开浏览器
npm run serve                # 只启动并打开浏览器，不做环境检查
npm start                    # 只启动，不打开浏览器
```

看到这样的输出就成功了：

```
服务已启动：http://127.0.0.1:8787/?token=xxxxxxxx（Ctrl+C 停止）
```

> **务必使用命令里打印的完整地址（含 `?token=...`）**。若配置了访问令牌，
> 不带令牌直接访问 `http://127.0.0.1:8787` 会被拒绝——这是防止本机其它程序调用接口的保护。

## 4. 首次配置（三步）

打开界面后进入 **设置** 页，按顺序填三块内容。**每块填完都要点该块下方的「保存配置」。**

### 第一步：邮箱账户（必需）

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| IMAP 服务器 | 收信服务器地址 | `imap.example.cn` |
| IMAP 端口 | 993（SSL）或 143（STARTTLS） | `993` |
| IMAP 加密 | 993/465 选「是」 | 是 |
| IMAP 账号 | 通常是完整邮箱地址 | `user@example.cn` |
| IMAP 授权码 | **客户端专用密码，不是网页登录密码** | （见下） |
| SMTP 服务器 | 发信服务器地址（**常与 IMAP 不同**） | `smtp.example.cn` |
| SMTP 端口 | 465（SSL）或 587（STARTTLS） | `465` |
| SMTP 账号 / 授权码 | 留空则复用 IMAP 的 | 同上 |
| SMTP 认证方式 | `auto` 失败时改 `LOGIN` | auto |
| 发件人姓名 / 邮箱 | 出现在你发出的邮件里 | 张三 / `user@example.cn` |

> **授权码怎么拿**：腾讯企业邮、网易、阿里等都在网页版邮箱的
> 「设置 → 账户 / 客户端设置」里生成"客户端专用密码 / 授权码"。它与你登录网页的密码不是一回事。
>
> **SMTP 服务器地址不要照抄 IMAP 的**。真实案例：企业邮箱的 IMAP 是 `imap.example.cn`，
> 而 SMTP 必须是 `smtp.example.cn:465`；写成腾讯企业邮的 `smtp.exmail.qq.com`
> 会一直报 `535 authentication failed, system busy`——这个报错看着像授权码错，其实是主机错。

填完点 **「测试连接」**，两项都通过再继续。

### 第二步：大模型（必需）

| 字段 | 说明 |
| --- | --- |
| API Key | DeepSeek 官方 API Key（<https://platform.deepseek.com> 获取） |
| 接口地址 | 默认 `https://api.deepseek.com`（任何 OpenAI 兼容服务都可） |
| 模型 | 默认 `deepseek-chat` |

点 **「测试连接」** 确认能通。大模型负责分类、起草、意图理解与总结；**筛选与计数由本机程序执行**。

> 建议把 API Key 放在 `.env` 的 `DEEPSEEK_API_KEY=` 里（见[第 5.18 节](#518-环境变量env)），
> 这样换电脑时密钥不落在 `data/config.json` 里。

### 第三步：日历（可选）

只做邮件的话可以跳过。要用 Google 日历请照[第 10 节](#10-google-日历配置详解)操作。

### 首次使用检查清单

- [ ] 设置页「测试连接」：邮箱 IMAP ✅ SMTP ✅
- [ ] 设置页「测试连接」：大模型 ✅
- [ ] 邮件总览页点 **「分析最近 24 小时」**，能看到统计与「需要你处理」清单
- [ ] 打开一封「需要你处理」的邮件 → 点「起草回复」→ 到「邮件草稿」审核 → 确认发送
- [ ] （可选）日历页「测试连接」→ 完成 Google 授权
- [ ] （可选）在设置页填好**邮件签名**（多行），草稿会自动带上

## 5. 配置项完整参考

配置有两个来源，**环境变量（`.env`）优先级更高**：

```
默认值（server/config/defaults.js）
   ↓ 被覆盖
data/config.json（界面「设置」写这里）
   ↓ 被覆盖
.env（推荐只放密钥）
```

### 5.0 首次配置向导（「开始使用」）

全新安装后**第一次打开会自动进入**「开始使用」页，把首次配置压成三步：

| 步骤 | 要做什么 | 怎么算通过 |
| --- | --- | --- |
| 1. 连接邮箱 | 填 IMAP/SMTP 服务器、端口、账号、授权码、发件人 | 点「保存并测试」→ 真的连一次 IMAP 与 SMTP |
| 2. 配置大模型 | 选服务商预设（或自定义地址）→ 填 API Key 与模型名 | 点「保存并测试」→ 真的发一次请求 |
| 3. 连接 Google 日历 | **可选**，不用可以点「跳过这步」 | 「连接 Google 日历」授权后刷新状态 |

- 「保存并测试」会**先保存再验证**：没过就停在当前步并把原因写出来，通过了会自动进入下一步。
- 配置没配完时，**总览页顶部会有一条横幅**说明还差哪一步，导航「开始使用」上也有提示点。
- 字段只保留跑起来必需的；更细的项（起草口径、日历回顾阈值、通知、代理等）都在「设置」里。
- 这一步的进度来自 `/api/health`（**纯本地判断，不连网**），所以刷新很快；真要连出去的检查在「设置 → 运行自检」。
- 配好之后，三步的图标都会变成 **✓**，最后一枚「**可以用了**」也是 ✓（它本来只在配好后才出现），
  停在它上面时会高亮。
- 这页顶部有「**返回设置**」：向导是从「设置 → 外观」里点开的，所以回去时会**直接滚回「外观」那张卡片**
  并短暂高亮（靠设置页区块的**具名锚点**，见 5.16）。

> 已经配好了还想重看？导航里的「开始使用」即可，它同时也是"当前状态一览"；
> 配置完成后该入口会**自动从导航隐藏**（避免噪音），随时可以从「设置 → 外观 → 打开『开始使用』向导」再进来。

### 5.1 外观模式（浅色 / 深色 / 绿色）

顶栏右侧有三颗按钮，点一下立即切换，**不需要保存、也不影响服务端**：

![三种外观模式](assets/theme-preview.png)

| 模式 | 气质 | 适合 |
| --- | --- | --- |
| 浅色 | 白底深字、浅蓝强调 | 明亮环境、投屏、截图 |
| 深色 | 中性深灰蓝、亮蓝强调 | 长时间阅读（**默认跟随系统**） |
| 绿色 | 深绿底、亮绿强调 | 编辑式深色，参考 [bartoszkolenda.com](https://bartoszkolenda.com/) 的气质 |

- 选择存在**浏览器本地存储**（键名 `mailbot.theme`），不会写进 `data/config.json`；换浏览器或换电脑需要重选。
- **没点过的时候跟随系统**：系统是深色就深色、是浅色就浅色，因此升级后外观不会突变；
  系统外观变化时也会自动跟着变（前提是你没手动选过）。
- 想恢复「跟随系统」：清除该站点本地存储里的 `mailbot.theme` 后刷新页面。

### 5.2 首屏分析时间段

总览页标题右侧有一个**时间范围选择器**（`最近 24 小时 / 3 天 / 7 天 / 30 天 / 自定义时间段…`），
与分析按钮**在同一行**：

- 选择后**标题与分析按钮都跟着变**（例如「最近 7 天」），总览数据也按新窗口重新取。
- 放长假回来：选「最近 7 天」，或用「自定义时间段…」选「放假前一天 ~ 今天」。
- 点分析会**先弹出预检**，把代价摆出来再动手：

  ```
  最近 7 天内共 312 封邮件
  本次将取出最新 312 封（上限 420）
  其中 40 封已分析过，不会重复消耗
  预计新增分析约 272 封 · 约 23 次模型调用
  ```

- 预检是**只读**的（只连一次邮箱数封数），**不消耗任何 token**；实测约 0.8~1.5 秒，
  这期间按钮会变成「预检中…」并置灰，避免连点。
- 若窗口内邮件超过取信上限，会明确写出「超出上限的 N 封本次不会分析」——
  宁可让你知道漏了，也不假装都分析过了。

> **「一句话总结」只反映当前窗口**。切到某个窗口但还没分析时，总结会按当前统计现场生成，
> 并提示「上一次 AI 简报针对的是最近 24 小时」——不会出现"最近 7 天"配"近 24 小时"的矛盾。
> 想看到该窗口的 AI 总结，点一次「分析最近 X 天」即可。
>
> 该选择只在当前会话有效（切页保留，刷新回到 24 小时）；
> 想改默认窗口请改设置里的「回看窗口」。
>
> 总览页**没有「刷新」按钮**：数据变更（含定时任务跑完）会自动让页面重新取数。

### 5.3 换一个大模型服务商

「设置 → 大模型 → 服务商预设」下拉框，选中后自动填入 Base URL 与常用模型名：

| 预设 | 是否国内直连 | 备注 |
| --- | --- | --- |
| DeepSeek 官方 | ✅ | 默认，便宜 |
| 阿里云百炼（通义千问） | ✅ | 需在百炼控制台开通 |
| 月之暗面 Kimi | ✅ | 长上下文 |
| 智谱 GLM | ✅ | `glm-4-flash` 有免费额度 |
| 硅基流动 SiliconFlow | ✅ | 一个 Key 聚合多家开源模型，模型名带「组织/」前缀 |
| OpenAI | ❌ 需网络出口 | 国内需自备出口，本程序不使用系统代理 |
| OpenRouter（聚合） | ❌ 需网络出口 | 模型名带厂商前缀 |
| 本地部署（Ollama / vLLM） | ✅ 完全离线 | **API Key 可留空**，需先 `ollama pull` 拉模型 |

- 只改 Base URL 与模型名，**不会清空你已填的 API Key**（换服务商后需要你重新填写）。
- 若你现在用的是自建网关地址，下拉框会显示「自定义」并**原样保留**该地址，不会被预设覆盖。
- 判断"是否需要 Key"看的是解析后的 hostname 是否属于本机/私有网段，所以公网地址仍然必须填 Key。
- 小提示：**本地小模型对中文邮件的分类与起草质量明显弱于在线模型**，建议只用于离线试用或隐私敏感场景。

### 5.4 时间显示与发送时间
- 界面上所有时间（邮件时间、生成时间、「今天/昨天」的判断）都按**设置 → 日历时区**渲染，
  而不是浏览器所在时区。出国出差时不会出现「邮件明明下午 4 点、界面显示早上 8 点」。
- 发送出去的邮件，`Date` 头按同一时区写成带偏移的形式：`Thu, 01 Oct 2026 11:41:49 +0800`。
  这样 Foxmail 等客户端显示的是本地时间，而不是 UTC。

### 5.5 附件

**收到的附件**：详情弹窗 →「原始邮件」页签，列出附件名/类型/大小，每行「保存」。
附件内容早在分析时就随原文一起归档在 `data/raw/`，所以**列清单与下载都不连邮箱、不重新下载**。

- Chrome/Edge 点「保存」会弹出系统"另存为"，**目录与文件名都能自己选**；Firefox/Safari 只能存到默认下载目录。
- 在"另存为"里点取消，不会再偷偷下载一份。
- 文件名会先做安全收敛（去掉路径、控制字符、开头的点），所以对方邮件里写 `../../evil.sh` 也只会存成 `evil.sh`。

> **本程序刻意不提供"让服务端把附件写到指定路径"**。那等于给网页一个任意文件写入能力，
> 一封构造过的 HTML 邮件就可能被利用。要选目录请用浏览器的"另存为"。

**发出的附件**：草稿编辑器的「附件」区，点「选择文件」或拖拽。

- 体积按 **base64 编码后**算（默认上限 20 MB，可在设置里改）。编码膨胀约 1/3，
  所以 18 MB 的文件编码后 24 MB —— 一定会被企业邮箱拒收，因此界面会提前禁用发送按钮。
- 发送确认框会逐项列出附件名与大小。
- 发送成功后附件内容会从本机删掉（记录保留，便于回看"这封发了什么"），因为它已随邮件存在服务器上。
- 删除草稿会一并清理附件文件，`data/attachments/` 不会留孤儿。

### 5.6 密钥存储（系统钥匙串）

到「设置 → 密钥存储」。**默认是"明文写在配置文件里"**，搬进系统钥匙串需要你手动点一次。

纳入保管的密钥一共这些（设置页会**逐项**列出它们现在到底在哪）：

| 密钥 | 默认位置 |
| --- | --- |
| 邮箱授权码（收信 / 发信） | `data/config.json`（每个邮箱实例各一份） |
| 大模型 API Key | `data/config.json` 或 `.env` |
| 界面访问令牌 | `data/config.json` 或 `.env` |
| Google 客户端密钥（Client Secret） | `data/config.json` 或 `.env` |
| **Google 刷新令牌**（refresh token） | `data/google-token.json`（权限 600） |

#### 先说清楚它能防什么、不能防什么

| | |
| --- | --- |
| ✅ **能防** | `config.json` / `.env` / `google-token.json` 被拷走、被网盘同步、进了备份包、被人翻到——文件里不再有密钥，密文只有**这台机器的这个用户**解得开 |
| ❌ **不能防** | 以你的身份运行的恶意程序、你离开时没锁屏的电脑、你自己点开的钓鱼页面 |

换句话说：它解决的是"**凭据散落在明文文件里**"，不是"你的电脑被入侵"。

#### 各平台用什么后端

| 平台 | 后端 | 存哪 | 换电脑会怎样 |
| --- | --- | --- | --- |
| Windows | `dpapi`（系统数据保护 API，CurrentUser） | `data/secrets.dpapi`（密文） | 解不开，需重新填授权码、并重新连接一次 Google 日历 |
| macOS | `keychain`（系统钥匙串） | 钥匙串条目 `mailbot-secrets` | 同上 |
| Linux | `libsecret`（`secret-tool`，GNOME Keyring / KWallet） | Secret Service | 同上；**无桌面环境的服务器上通常没有它** |
| 任意 | `file`（**未加密**） | `data/secrets.json`（权限 600） | 能拷走（所以它只是"挪个地方"，不是加密） |

> ⚠️ `auto` 会优先挑**加密**的后端；一个都没有时只能退到 `file`——
> 这种**降级会在设置页明确提示**，不会让你误以为已经加密了。
> 降级到 `file` 时，Google 刷新令牌也不过是从一个 600 权限的文件搬到另一个 600 权限的文件，
> **保护强度并没有提高**（设置页与迁移后的提示都会这么写，不粉饰）。

#### 每个后端"验证到什么程度"（诚实清单）

这张表说的是**被证明了的**事，不是"我们相信是这样"。每一行都能在
`test/secrets-platform.js` 里找到对应用例，CI 每次 push 都会跑（三平台矩阵）。

| 后端 | 保护强度 | 自动化里验证到什么程度 | 怎么验的 |
| --- | --- | --- | --- |
| Windows `dpapi` | 密文与本机**当前 Windows 用户**绑定（DPAPI `CurrentUser`）；换机器或换账户都解不开 | **CI 真跑**（`windows-latest`）：写入 → 读回 → 校验一致 → 清除，并断言密文确实落盘、密文里**不含**明文、清除后读不到 | 起 `powershell` 调 `ProtectedData`，全程走真实代码路径 |
| macOS `keychain` | 由系统钥匙串加密保管 | **CI 真跑通过**（`macos-latest`，2026-10-07 run 37630721977 日志实证：`✓ macOS 钥匙串：临时钥匙串 + 搜索列表把它排在第一位的真跑往返`）：写入 → 读回 → 校验一致 → 清除整条往返；钥匙串用 `security create-keychain` 临时建，**不碰你的登录钥匙串**，用例结束（含失败）就删掉。此前这条作业连续红过三轮（断言写错、`-k` 旗标不存在、macOS 26 的 hex 打印），**绿灯之前这里写的一直是"未通过"**，没有提前说成已验证 | 临时钥匙串 + 后端把**写/清**指向它；**读**靠把**搜索列表**里的临时钥匙串排到**第一位**（`security` 的读命令没有"指定钥匙串"的选项），结束时**严格还原并核对一致**；隔离是否成立由"写一个探测值 → 用后端同款读法原样读回"裁判（这一条从不为让红变绿而放宽）；读回来的原始输出若是 `security` 的**十六进制打印**，按 `decodeKeychainOutput()` 还原（见下面的边界说明） |
| Linux `libsecret` | 由桌面钥匙串（Secret Service）保管；无桌面会话的服务器上通常不可用 | **CI 真跑已通过**（`ubuntu-latest`，2026-10-07 run 37630721977 日志实证：`✓ Linux libsecret：真实 Secret Service 往返 … 真跑通过：真 D-Bus 会话 + 真 gnome-keyring + 真 secret-tool`）：CI 里先装 `libsecret-tools gnome-keyring` 并自建 D-Bus 会话（`dbus-run-session` + 解锁钥匙环），跑的是真实 Secret Service 往返。**若 runner 上起不来**，用例会**显式跳过并打印原因**——那时这里必须写「libsecret 未被真实验证」，不许含糊过去；"命令级"用例（用测试自己生成的**假 `secret-tool`** 断言 `store`（密钥走 stdin）/`lookup`/`clear` 拼得对）只是兜底，**不能替代**真跑结论 | 真跑用例 + 命令级用例（两条都在 CI 日志里能看到结论） |
| 任意 `file` | **没有加密**：只是把密钥从 `config.json` 挪到一个 600 权限的单独文件 | 三平台都跑：断言"退到 `file` 必然可见"——`degraded` 标记、原因里出现"未加密"、迁移结果与后端文案同样标注；**不允许静默降级** | 把系统后端"藏起来"（PATH 指向空目录）后检查报告口径 |

几条**如实说明**的边界，别当成 bug：

- **macOS 写入时密钥会在本机进程参数里出现一下**：`security` 只支持把密码作为参数传入（没有 stdin 形式）。
  DPAPI 与 `secret-tool` 都走 stdin，不进 argv——这一点由 Linux 的命令级用例直接断言（明文不得出现在 argv 里）。
- **macOS 26（Tahoe）上 `security` 可能把数据以十六进制打印**，读回来时是 `7b0a2020…` 这种纯 hex
  文本，而不是原文。触发条件是"内容不是干净的可打印单行文本"——我们保管库的载荷是**带换行的
  pretty JSON**，正好中招（CI run 37629230504 的 macOS 作业实测：334 个 hex 字符，**正好**是那份
  JSON 的字节数两倍；同一次运行里短小的单行探测值却是原样回来的，所以既不是"读失败"也不是"写坏"）。
  后端会用 `decodeKeychainOutput()` 还原：只认"偶数长度的纯 hex + 解出来是合法 UTF-8 + 解出来是
  JSON 对象"三条同时成立的情况，任何一条不满足就**原样返回**（宁可让后面的 JSON 解析带着原始输出
  报错，也不把原文悄悄改坏）。`security` 不告诉你这次打印的是原文还是 hex，所以"某段文本恰好既是
  合法 hex、解码后又恰好是 JSON 对象"在原理上无法区分（例如 `7b7d` → `{}`）；我们的载荷形状固定、
  不会撞上，这一点如实写在这里而不是假装万无一失。

- **macOS 用例会临时改一次机器的"钥匙串搜索列表"，结束前严格还原并核对**：`security` 的读命令
  （`find-generic-password`）**没有**"指定去哪个钥匙串找"的选项——它末尾那个钥匙串位置参数只是
  "搜索列表兜底"语义，搜索列表里命中同名旧条目时就轮不到它。所以要让"读"确实落到临时钥匙串，
  唯一可靠的办法是把**临时钥匙串放到搜索列表第一位**。两个实测细节值得记下来（都是 CI 打的原始输出）：
  - 设完之后列表里**仍会留着只读的系统钥匙串**（`/Library/Keychains/System.keychain`，root 属主、
    用例写不进去），所以断言的是"临时钥匙串**排第一** + **登录钥匙串不在列表里**"，而不是"列表只有一项"——
    后者是上一版的写法，它红了，错的是断言而不是隔离；
  - `security` 回显的路径可能带 `/private` 前缀（`/var/...` 与 `/private/var/...` 是同一处）、
    名字的 `-db` 后缀也可能时有时无，比较"是不是同一个钥匙串"时必须先归一这两处。
  因为搜索列表是**全局机器状态**，用例做了三件事：
  ①改之前先记下原始列表；②无论成功失败都在 `finally` 还原；③**用例内部断言**"最终列表已还原"，
  不一致就把原始值与现值一起打出来。登录钥匙串的内容一个字节都不会被改（只读它的条目存在性，
  且**不带 `-w`**、带超时，不触发任何弹窗）。写与清除仍然只用钥匙串位置参数指向临时钥匙串。
  唯一兜不住的情况是进程被 **SIGKILL**（`finally` 不会执行，搜索列表会停在"临时钥匙串排第一 + 系统钥匙串"上）——
  CI 是一次性的 runner，本机跑也只是临时改一次自己的搜索列表。

- **MAC/Linux 的真跑能力依赖"能不能起子进程"**：某些受限沙箱会禁掉管道子进程（报 `EPERM`）。
  那种环境里这套用例会**如实报"系统后端不可用 + 拒绝迁移 + 明文未动"**并写明原因，而不是假装验证过；
  真机往返交给 CI。
- **`auto` 落盘记的是实际后端**（例如 `file`），不是 `auto` 这个字面值——否则换台机器再打开会看着像"加密的"。

#### 迁移与迁回

点「迁入」后程序按这个顺序做，**任何一步失败都不会留下半个状态**：

1. 收集当前正在用的密钥（含 `data/google-token.json` 里的 Google 刷新令牌）；
2. 写进保管库；
3. **读回来逐项比对**；
4. 比对通过后，才把 `config.json` 里的明文清空、把 `.env` 里那几行清空、
   **删掉 `data/google-token.json` 这个明文令牌文件**、并记下用哪个后端。

第 1–3 步失败时**明文文件一个字节都没改**。第 3 步不一致（"搬过去打不开"）还会把写坏的内容清掉再报错。

> **Google 刷新令牌是这条规则里最要紧的一项**：弄丢它 = 你必须重新授权一次。
> 所以"写失败 / 读回不一致 → 绝不抹掉明文令牌文件"是硬约束，与配置文件同样的口径。
> 迁移完成后换机器（或换 Windows 账户）时密文解不开，需要**重新连接一次 Google 日历**。

「迁回明文」把密钥写回原处并**清空保管库**（避免同一密钥存在两处）：
配置类的写回 `config.json`，Google 刷新令牌写回 `data/google-token.json`（权限 600）。
令牌是**先写回原处、成功之后才清保管库**——中途出错也不会丢令牌。

#### 几个刻意的行为，别以为是 bug

- **`"***"` 仍然表示"保持原值"**：密钥搬到保管库之后界面里显示的仍是掩码，保存设置不会把它弄丢。
- **`.env` 里的值会被搬走并把那一行清空**（键名保留）——它是我们自己的配置文件，明文留在那里等于没搬。
- **真实环境变量里的密钥不会被搬**（容器/系统环境里设的那种）：程序改不了它，抄一份只会让同一密钥存在两处。
- **保存配置不会顺手搬运环境变量里的密钥**，只有「迁入」按钮才会真正搬。
- **迁移过保管库、但后来才做的 Google 授权**：新令牌会**直接写进保管库**（不进明文文件）；
  反之，如果迁移时还没有 Google 令牌，之后连的 Google 令牌会以明文落 `data/google-token.json`，
  设置页会明确提示"尚未纳入"，再点一次「迁入」即可。
- **备份包不含保管库内容**：密文与本机绑定，拷到别的电脑解不开，导出时会在"不含"清单里写明。
  勾了「包含密钥」时，Google 令牌会从**它当前所在的地方**取（保管库或明文文件），不会漏。

#### 出问题了怎么查

| 现象 | 原因 / 怎么办 |
| --- | --- |
| 设置页说"保管库读取失败" | 密钥**没有被删除**，只是本次没注入。Windows 上常见于**换了 Windows 账户**或从别的机器拷来了 `secrets.dpapi`；改回 `vault.mode = "config"` 并重新填授权码，或删掉 `data/secrets.dpapi` 后重填 |
| 日历页说"令牌读不出来"（错误码 `GOOGLE_TOKEN_VAULT_ERROR`） | 保管库解不开（换了机器/账户）。令牌还在，只是读不出来：重新连接一次 Google 日历即可；也可以到「设置 → 密钥存储」点「迁回明文」拿回一份明文副本 |
| 「迁入」报"写入保管库失败" | 看具体信息。Linux 上没有 `secret-tool` 时请选 `file`（并知道它不加密）或继续用默认的明文方式 |
| 「迁入」报"校验不一致" | 说明这个后端写进去读不出来。程序已回滚，密钥（含 Google 令牌）仍在原处；换一个后端（比如 Windows 的 `dpapi`）再试 |
| 想彻底改回明文 | 点「迁回明文」；之后**别把 `config.json` / `google-token.json` 放进网盘或提交到仓库** |
| 忘了自己用的是哪种 | 「设置 → 密钥存储」列出了**每一个密钥现在到底在哪**（明文配置文件 / .env / 明文令牌文件 / 保管库 / 未设置） |

### 5.7 备份与恢复

到「设置 → 备份与恢复」。**换电脑、重装、误点「重置数据」之前请先导出一份。**

**导出**得到的是一份标准 zip（Windows 自带解压器就能打开），里面有：

| 包内文件 | 说明 |
| --- | --- |
| `README.txt` | 先看它：里面写了这一包含什么、不含什么、怎么恢复 |
| `manifest.json` | 清单与统计（程序导入时靠它校验格式） |
| `state.json` | **最重要**：分析结论、草稿、待办状态、简报索引 |
| `config.json` | 配置 |
| `audit.jsonl` | 操作台账 |
| `reports/` | 历次简报原文 |
| `raw/` | 邮件原文（**仅当勾选「包含邮件原文」**，体积很大） |
| `.env` / `google-token.json` | **仅当勾选「包含密钥」** |

**默认不含任何密钥**，所以可以直接放网盘；勾了「包含密钥」之后包里就是明文授权码 / API Key /
Google 令牌，界面会红字警告，**别通过聊天工具或邮件发出去**。

> Google 令牌可能已经搬进了保管库（此时 `data/google-token.json` 已被删掉）。
> 因此导出时会从**它当前所在的地方**取：托管在保管库就取保管库里的那份，
> 明文文件还在就取文件——不会出现"勾了包含密钥、包里却没有令牌"的假象。
> 反过来，**保管库本身的内容永远不进备份包**（密文与这台机器绑定，拷过去也解不开）。

**恢复**：选择之前导出的 zip。程序会**先显示里面有什么、缺什么**（含"导入后需要你补填哪些"），
确认后才覆盖。三重保护：

1. 必须显式确认；
2. **覆盖前自动把当前数据存一份**到 `data/backups/pre-import-*.zip`（列表就在同页，可回滚）；
3. 只按白名单落盘，压缩包里其它文件一律跳过并如实报告。

> **导入不会清空你现在的密钥**：备份里密钥为空时，会保留**磁盘上 `config.json` 里的值**
> （刻意不从内存读——内存里的值可能来自 `.env`，那样一次导入就把密钥抄进了 `config.json`，
> 正好和"密钥只放 `.env`"的建议相反）。所以你可以放心用"不含密钥的备份"恢复数据。
>
> Google 令牌不在 `config.json` 里，导入时按文件落盘：包里带 `google-token.json` 就写成明文文件，
> 不带就**不动**你现有的令牌（保管库里的那份也不会被碰）。

导出的压缩包里有中文文件名，用的是 UTF-8 标志位；文件损坏（CRC 不符）时导入会明确报错，
不会"恢复"出一堆坏数据。

### 5.8 存储与清理（数据保留）

到「设置 → 存储与清理」。**默认什么都不自动删**——清理会影响"历史还能不能查到"，必须由你开启。

先把两件事分清（界面上也这么写）：

| | 存哪 | 清了会怎样 |
| --- | --- | --- |
| **结论**：摘要、待办、优先级、统计、图表、简报、台账 | `state.json` / `reports/` / `audit.jsonl` | ——（**清理原文不会动它们**） |
| **原文**：整封邮件 + 附件 | `data/raw/*.eml` | 只影响「查看原文 / 下载附件 / 重新起草」 |

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| 分析记录上限 | `3000` | 超出后删**最旧的**。⚠️ 这是**历史记录本身**的上限：调小会让旧邮件从列表/统计/搜索里消失（旧版本写死 3000，现在可调） |
| 归档原文保留天数 | `0`（永久） | 设为正数后会删掉超期的原文。邮件还在服务器上时程序会**回连邮箱重取**（`loadRawFor` 有兜底），**邮件已被删除或超出服务器保留期时就查不到了**；**不会自动删**，要手动点按钮 |

存储占用表里有**两项体检**专门回答"我到底能省下多少"，表下面还会写出当前保留策略：

- **可回收空间**：按**与你实际删除时完全相同**的判据算出来（同一个函数 `planRawCleanup`），
  分「超期」与「孤儿」两类给出条数与字节数——所以**显示多少，点下去就能删多少**，
  不会出现"显示 40 MB 可回收、真删只删了 2 MB"。
- **data 目录合计**：整个 `data/`（原文 / 简报 / 台账 / 附件 / 证书）的占用；清理原文后这一项应当下降。
- 保留天数为 `0` 时，这里会明写「**当前为永久保留，保留期清理不会删除任何原文**」，
  而不是给一个含糊的 `0`。

两个按钮：

- **清理孤儿文件**（零风险）：删除**没有任何分析记录指向**的 `.eml`。分析记录被容量收敛后，这些文件已经没有任何界面入口能访问，删了不损失任何可查询的历史。
- **按保留期清理原文**：需要先把保留天数设为大于 0 并保存（**服务端只认保存过的配置**：
  请求里带的天数不能绕过"永久保留"，否则"我明明设了不删、原文却没了"）。删除是**不可逆**的，
  会二次确认。界面**不预选任何破坏性选项**——不点按钮、不做二次确认，什么都不会删。

#### 会删哪些、绝不删哪些

一个 `.eml` 算不算"过期"，取下面两者中**较新**的那个时间：

1. 文件自己的修改时间（归档 / 回连重取的时间）；
2. 指向它的分析记录里最新的 `analyzedAt`（程序最近一次处理这封邮件的时间）。

**只要其中之一在保留期内，就保留。** 这就是"仍被近期分析引用的原文不会被删"的判据：
文件时间戳会骗人（改时间戳、从备份复制、重新分析时原文读取失败但结论已更新），
而分析记录才是"程序最近还在引用这封邮件"的真实证据。判据刻意偏保守——
少删一个只多占几 MB，误删一个（邮件已被服务器删除时连回源都拿不回来）就永久失去了。
被这条规则保护下来的文件，清理结果里会单独报出数量。

孤儿文件不受保留期影响：它们本来就没有任何入口，清不清都是零风险（可用"清理孤儿文件"单独清）。

#### 清理结果会如实报出"释放了多少"

每次清理返回并显示：

- **删除了多少个**文件（孤儿几个、超期几个）；
- **释放了多少字节**——精确值 = 逐个被删文件 `stat.size` 之和，只统计**确实删成功**的文件；
  MB/GB 只是展示形式，界面会同时给出原始字节数。**不做估算、不四舍五入**：
  `16384` 字节曾经被显示成「释放约 0 MB」，用户合理地以为清理没生效；
- **删除前 → 删除后**的 `data` 目录占用；
- 跳过了多少、为什么跳过（仍在保留期内 / 永久保留 / 被近期分析保护 / 删除失败及原因）。

一个都没删时同样给出明确说明（例如"当前为永久保留……不会删除任何原文"或
"没有需要清理的文件：全部都还在保留期内"），不会用一句"已删除 0 个"含糊过去。

> ⚠️ **删除原文不可逆**：删了就不能再查看这些邮件的原文，附件也下载不了。
> 界面上写明这一点，并且二次确认对话框是**危险色**按钮；清理结果出来后会在页面上留一条记录
> （不是只有几秒就消失的提示条）。
>
> 每次清理都会写进**操作台账**（`storage.cleanup`，含孤儿数/超期数/**释放字节**/被保护数/清理前后占用）——
> 删原文是永久损失，事后必须能回答"我的邮件原文是什么时候没的"。
>
> 顺带一提：归档**不会自动增长到失控**，但也不会自己缩小。`state.json` 里超过上限的分析记录会被
> 自动收敛，而原文文件**不会**跟着删——这就是"孤儿"的来源，也是这个页面存在的原因。


### 5.9 局域网加固（想让别的设备也能用时）

默认只监听 `127.0.0.1`：**只有这台电脑能访问**，这是最安全的设置。一旦改成 `0.0.0.0`，
同一网络里的其他设备就能连上，这时必须把下面几件事做对。

#### 1. 一定要有访问令牌

监听地址不止本机时，启动日志会**列出局域网可达地址**并逐条警告；没有令牌会直接标红。
到「设置 → 访问与安全」点「生成新令牌」（32 字节随机串），然后用它登录。

> 令牌只显示一次。**改令牌会让所有已登录设备立即掉线**——这正是它的用途。

#### 2. 登录方式变了（会话 Cookie）

浏览器**不再保存令牌**：登录时用令牌换一个 `HttpOnly` 的短期会话 Cookie
（`SameSite=Strict`，空闲 12 小时过期、最长 7 天必须重新登录）。这解决了三个老问题：
令牌不再进浏览器历史与代理日志、不再永不过期、可以单独登出。

- 重启服务会让所有会话失效（会话只在内存里，这是刻意的）。
- 忘记令牌：在服务器的「访问与安全」里重新生成（或看 `data/config.json` 的 `web.authToken`、`.env` 的 `MAILBOT_WEB_TOKEN`）。
- 命令行/脚本仍可用 `x-mailbot-token` 头访问接口。

#### 3. 建议开 HTTPS

局域网内 HTTP 是**明文**：同网段的人能在链路上看到访问令牌与邮件内容。

| 方式 | 说明 |
| --- | --- |
| 自有证书（推荐） | 填 `certFile` / `keyFile`（PEM）。浏览器不会警告，界面会显示指纹 |
| 自签证书 | 勾选即自动生成到 `data/tls/`（含 SAN、825 天、快过期自动重签）。**浏览器仍会提示"不受信任"**，点继续访问即可——传输仍是加密的 |

> ⚠️ 配置了 HTTPS 却拿不到证书时，程序会**启动失败**而不是退回明文。
> 这是有意的："以为走了 HTTPS、其实在明文传令牌"比"起不来"严重得多。

#### 4. 域名访问要登记

服务只接受 `localhost` / 回环地址 / IP 字面量作为 `Host`。要用域名（反向代理、内网域名）
必须在「允许的域名」里登记。其余域名一律拒绝——**这是防 DNS rebinding 的关键**：
攻击者可以把自己的域名解析到 127.0.0.1，让浏览器把请求打到你的本机服务上，
那时 `Origin` 看起来还是同源的，只有 `Host` 头藏不住。

#### 5. 别把反向代理的 X-Forwarded-For 当默认

`web.trustProxy` 默认关闭。打开它意味着**来源 IP 由代理说了算**——
只有在确实有可信代理时才开，否则失败限速会被伪造的 IP 绕过。

#### 出问题

| 现象 | 原因 |
| --- | --- |
| 打开页面变成「需要访问令牌」 | 这是登录页，输入令牌即可；输错超过 10 次会被临时拒绝（5 分钟） |
| 别的设备打不开 | 检查监听地址是否 `0.0.0.0`、防火墙是否放行端口、是否用 http:// 访问了 HTTPS 端口 |
| 返回 421 | 你用的域名没登记在「允许的域名」里 |
| 返回 429 | 登录失败次数过多被临时限速（默认 5 分钟内 10 次） |
| 重启后要重新登录 | 预期行为：会话只存在内存里 |

### 5.10 数据去向（隐私）

到「设置 → 数据去向」。这里的内容是**按你当前配置推导**的，改了模型地址或代理，
表里的目的地就会跟着变——不是一份写死的说明。

**会离开这台电脑的**：

| 功能 | 发什么 | 发给谁 |
| --- | --- | --- |
| 分析邮件 | 主题、收发件人与抄送地址、**正文前 N 字符**（默认 4000，可调）、**附件文件名**、时间 | 你配置的大模型地址 |
| 起草回复 | 同上 + 你的签名与起草偏好 | 同上 |
| 对话查邮件 | 你的问题 + 命中的邮件片段 | 同上 |
| 日历 | 日程标题/时间/地点/描述/参与者邮箱 | Google Calendar |
| 自寄简报 | 统计数字与要点 | 你的邮箱 |

**不会离开的**：附件内容（只有文件名会被发送）、邮箱授权码（只用于连 IMAP/SMTP）、
邮件原文归档与附件文件、分析结果/草稿/简报/台账、访问令牌与会话。

#### 仅本地模式

打开后，邮件内容**只允许**发给本机（回环地址）上的模型，任何其他地址都会被**直接拒绝**：

```
已阻止：api.deepseek.com 是公网服务，邮件正文会离开本机并经过第三方服务器。
```

要点：

- **局域网地址也算"离开本机"**：`192.168.1.50` 是另一台电脑。Ollama 跑在同一台机器上
  用的是 `http://127.0.0.1:11434`；确实把模型跑在别的机器上，就不该开这个开关。
- 拦截发生在 `LlmClient` 构造函数里（所有模型调用的唯一入口），所以**不会有漏网之鱼**。
  打开后如果模型地址不对，点「测试」会立刻告诉你原因。
- 默认**关闭**（升级上来的用户行为不变）。

### 5.11 跟催（我承诺了什么 / 等谁回复）

到导航「**跟进**」页的「**跟催**」页签（「跟进」是一个菜单项、两个页签：
**跟催**与[时间线](#512-按项目时间线)，页内一键切换）。
它回答收件箱答不了的两个问题：**我答应过别人什么**、**我在等谁回话**。

#### 两半的来源不同，成本也不同

| 栏目 | 怎么来的 | 花不花钱 |
| --- | --- | --- |
| **等对方回复** | 我发出的邮件带 `messageId`，进来的邮件带 `In-Reply-To`/`References` —— **本地纯比对** | **不花钱** |
| **我承诺了什么** | 用模型读**我自己发出的邮件**（`status=sent`，数量很少，一次调用） | 花一次模型调用 |

点「立即扫描」时界面会说明这一点；接口也要求 `confirm=true`，与"分析邮件"同样的规矩。

#### 哪些不算"在等对方"

- **纯回执**：「收到」「好的，谢谢」「嗯嗯，辛苦了」——这是回完就结束，不是等对方；
- **刚发出去的**：未超过 `followUp.waitHours`（默认 24 小时）不算，免得刚发完就催自己；
- **我说我会回复**：「收到，我看看再答复你」属于**我的承诺**，不是等对方。

> 这些判据都是启发式的，会有误差。设计上宁可少报也不要误报：
> 一个老是误报的跟催列表，用户会直接不看它。

#### 什么时候会自动关闭

只有**确定性证据**——线程里能对上、对方确实回了——才自动关闭，并写明「对方已回复」。
其余一律留给你判断（宁可多留一条，也不要替你"以为完成了"）。

#### 状态与「需要你处理」一致

已处理 / 稍后提醒 / 忽略 / 恢复。唯一的区别：**恢复不删记录**——
跟催项是扫描出来的事实，不像待办那样"撤销标记 = 没发生过"。

#### 一个如实的限制

模型的措辞变了（比如从"周三前把报价发给李总"改成"把报价单发给李总"），
会产生一条**新记录**，旧的那条要你手动关闭。这是刻意的取舍：
键里带标题哈希才能让一封邮件里的多条承诺互不覆盖；而"自动把旧的关掉"
有把真实承诺静默关闭的风险——两害相权，留着让你关。

#### 相关配置

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `followUp.enabled` | `true` | 关掉后该页签仍可打开，但不会扫描 |
| `followUp.waitHours` | `24` | 发出多久还没回才算"在等对方" |
| `followUp.extractCommitments` | `true` | 是否用模型提取"我承诺了什么"（关掉就只剩本地那半） |
| `followUp.maxCommitments` | `20` | 一次扫描最多提取多少条承诺（每封邮件最多 3 条） |

每次「分析邮件」跑完后会自动做一次扫描（免费那半+提取那半）；失败**不影响**分析结果。

### 5.12 按项目时间线

到导航「**跟进**」页的「**时间线**」页签（旧链接 `#/timeline` 仍可用，会自动落到这个页签）。
它把**同一件事**的邮件、我发出的回复、跟催与日程按时间串成一条线，
用来回答"这个项目从头到尾发生了什么"——单看收件箱永远看不出来。

#### 项目标签是怎么来的

分析邮件时由模型给出一个**短标签**（2-8 字，如「华东区投标」）。提示词里有一条硬要求：
**能对上已知标签就必须照抄**（程序会把已有的标签列表一起喂给模型），
否则模型每次换个说法，时间线就会碎成一地。

确实不属于任何项目时标签是空的，这些邮件进「未归类」入口。

#### 标签飘了怎么办：重命名 / 合并

模型没有记忆，所以「华东区投标」「华东投标」「投标项目」这种碎片一定会出现。
在时间线页点「重命名 / 合并…」，**填一个已有项目的名字就是合并**：

- 那些历史记录的标签会被**一起改写**（否则时间线里旧的那一半还在）；
- 旧名字会记成**别名**，下次分析再遇到它也会自动归到目标项目；
- 完成后会告诉你改了多少条，并写进操作台账；
- 页面顶部会列出"已合并的旧名字 → 新名字"，让你知道标签为何收敛。

#### 时间线里有哪四类东西

| 类别 | 来源 | 说明 |
| --- | --- | --- |
| 📥 收到的邮件 | 分析记录 | 带摘要，需要回复的会标红 |
| 📤 我发出的 | 已发送的草稿 | 带收件人 |
| ⏳ 跟催 | 跟催页同一份数据 | 会区分是「我的承诺」还是「等对方回复」 |
| 📅 日程 | **本程序的操作留痕** | 见下面的局限 |

> ⚠️ **日程只包含本程序建/改过的**。日程的真身在 Google 日历上，本地只留了操作记录，
> 因此**别人直接在 Google 日历上创建的日程不会出现在这里**。
> 界面顶部也会这样写明——不能让用户以为这就是全部日程。
> 另外「未归类」视图**不包含日程**：台账里的日程没有项目标签，硬塞进去等于编造关联。

### 5.13 邮件 HTML 正文的渲染

在邮件详情的「原文」页签里，如果这封邮件有 HTML 版本，正文上方会出现两个按钮：
**纯文本**（默认）与 **渲染 HTML**。

#### 为什么默认是纯文本

- **更可信**：不受对方样式干扰，能看到原始换行；
- **更安全**：纯文本不可能带着"打开回执"。

#### 渲染时会被剥掉什么

渲染前会过一遍**白名单**（见 ``web/sanitize-html.js``）：

| 处理 | 对象 |
| --- | --- |
| **连内容一起删掉** | ``script`` / ``style`` / ``iframe`` / ``form`` / ``input`` / ``button`` / ``object`` / ``embed`` / ``svg`` 等 |
| **剥掉属性** | 所有 ``on*`` 事件（``onerror``、``onclick``…）与所有 ``style`` —— CSS 一样能把请求发出去做追踪，``position:fixed`` 还能做点击劫持 |
| **只拆标签、保留文字** | 不在白名单里的其它标签（否则你会看到一封**空白邮件**） |
| **安全化** | 外链加 ``target="_blank"`` + ``rel="noopener noreferrer"``；``javascript:`` / ``data:text/html`` 一律去掉（连 ``java\tscript:`` 这种控制字符绕过也会被识破） |

#### 远程图片默认不加载（重要）

邮件里的 ``<img src="https://…">`` 是**追踪像素**：只要加载，对方立刻知道你
**何时打开的、用的哪个 IP、打开了几次**。所以默认把地址留在 HTML 里但**不请求**，
按钮会显示 **「显示图片（已拦 N 张）」**。

- 点它才会真去取，并且会提示"对方可能因此知道你打开了这封邮件"；
- **内联图片不受影响**：附件里带的图片（``cid:``）本来就在本机，不算对外请求。

#### 其它

- 净化在**渲染那一刻**做一次；切回纯文本不重新解析。
- 服务端只负责**按需**把原始 HTML 交给前端（``/api/mails/:folder/:uid?html=1``），
  净化只有前端一份实现，便于审计。
- HTML **不会**进分析记录（那会让 ``state.json`` 迅速膨胀），取不到也不影响正文阅读。

### 5.14 定时分析与通知（主动性）

到「设置 → 定时分析与通知」配置。**默认关闭**——打开后程序会在设定时刻自己去连邮箱、
调大模型、分析邮件，**会消耗大模型额度**，所以必须由你明确开启。

| 配置项 | 说明 |
| --- | --- |
| 启用定时分析 | 总开关，默认关 |
| 每天几点跑 | 24 小时制、可多个，如 `08:30,18:00`；按**「日历时区」**计算 |
| 星期几 | `0=周日 … 6=周六`，默认 `1,2,3,4,5`（工作日） |
| 每次回看窗口 | 小时数，默认 24 |
| 页内提示 | 跑完在页面右下角弹一条（默认开） |
| 浏览器桌面通知 | 需要页面开着（可切到后台标签页）并授权；打开开关时会**立即申请权限** |
| 把简报寄给自己 | **唯一在你不打开页面时也能收到**的方式；只有确实有待办或新草稿时才寄 |
| 简报收件人 | 留空则发给你自己的发件身份 |

**设置页会显示实时状态**：定时器是否在跑、上次执行时间与结果（待办/草稿数）、上次失败原因，
并提供「立即试一次」——它不受设定时刻限制，用来确认邮箱与大模型都通。

几条行为约定（都是为了避免"以为开了其实没生效"或"被反复打扰"）：

- **同一时刻只跑一次**：用配置时区的 `YYYY-MM-DD HH:MM` 作幂等键，重启、tick 抖动都不会重复跑。
- **不与你手动触发的分析并发**：已有分析在跑就跳过本次。
- **失败也占住这个时刻**：否则"邮箱连不上"会变成每分钟重试一次，把日志和网络刷爆；
  失败原因会记在状态里，下一个时刻照常再试。
- **开关保存后立即生效**，不需要重启服务。
- **只在有事时打扰**：没有待办也没有新草稿时不发通知，只在日志里记一行。

> 排查：如果"上次执行"一直没更新，先看状态行的提示——「配置已开启，但定时器未运行」说明
> 需要保存一次配置或重启服务；也可以点「立即试一次」看邮箱与大模型是否都正常。

### 5.15 日历回顾分析

在「知识库 → 日历知识库」用一句话复盘过去一段时间，例如：

```
请详细分析过去 30 天的日历，并给出工作优化建议
上个月我开了多少会？时间都花在哪了
过去一年我的时间分配有什么问题
```

支持的区间：`过去 7/30 天`、`上个月`（自然月）、`上季度`、`过去一年`、自定义起止（最长一年，
可在配置里改 `calendar.review.maxRangeDays`）。

**分析结果包含**：时间去向（工作 + 生活两个视角）、会议负荷与按周趋势、结构性问题、可执行的优化建议；
可点「下载 Markdown」导出，文件名形如 `日程回顾-2026-09-03_2026-10-01.md`。

导出的 Markdown 有四部分，便于离线核对：

1. **AI 叙述**（五段式）；
2. **附录 C 图表**：字符条形图（按周负荷、时间构成、生活花在哪、主题、人名、时长分布）；
3. **附录 A 统计明细**：口径说明、总览表、生活分类表、按周表、Top 参与人/重复日程、问题清单；
4. **附录 B 日程清单**：按天列出的完整条目。

#### 两个视角（读懂数字的前提）

| 视角 | 含义 | 包含 |
| --- | --- | --- |
| **总占用** | "这段时间我被占了多少"——也就是你用日历标记忙碌的目的 | 工作 + 生活/个人事务 |
| **工作负荷** | "工作有多重" | 会议 + 独自工作 + 专注时间（**不含生活**） |

「和老婆孩子过结婚纪念日午餐」算**总占用**但不算工作负荷：它确实占了时间（要统计），但不是工作（不污染工作口径）。

**生活/个人事务**有独立统计：运动健身 / 家庭陪伴 / 餐饮 / 医疗健康 / 个人事务 / 休闲娱乐 / 休息 / 其他，
各自给出项数与小时，图表里单独一色。

**休假/外出**按**天**计，不进小时口径——一条「年假 9/5→9/7」按小时算是 48 小时，足以把其他数字压成零头。

只有四种条目**完全不计入占用**：已取消、你自己标了"不占忙"、你已拒绝的会、办公地点标注（跨全天，计入会虚增）。
报告会逐项说明未计入多少条、为什么——**生活事务不在其中**。

#### 三条要注意的口径

- **会议识别走双通道**：有参会人 → 会议；没有参会人但标题像「与某某讨论/核对/评审」→ **也按会议计**，
  并说明其中多少场是按标题识别的。因为很多人把与会对象写在标题里而不加参会人，
  只认参会人字段会把"天天开会的人"算成"0 场会"。
  程序**不会**建议你补全参会人——这只是记录习惯不同，不是数据缺陷。
- **生活事务不是噪音**：如果你用日历标记"这段时间我占用了"（包括运动、家庭、个人事务），
  它就是分析对象之一：计入总占用、有独立的分类统计与图表，报告也必须同时覆盖工作与生活。
  真正不计入的只有已取消 / 不占忙 / 已拒绝 / 办公地点标注这四种。
- **记录稀疏时会提示**：如果总占用只占工作时段不到 20%，报告会写明"未记录 ≠ 真实空闲"，
  避免把"没写进日历的时间"当成可用空闲时间。

#### 去哪看"时间被谁占用最多"

报告与界面里都有「占用时间最多的人」。它有两个来源，并会标注：

- **参会人**（标准做法）：活动里邀请了谁；
- **标题解析**：从「与家诚、柳鑫讨论…」里抽出的名字。

后者是为"把与会对象写在标题里、不单独加参会人"的记录习惯准备的。
解析规则**保守优先**：只认「与/和/跟/同 + 名字 + 会议动词」这个结构，
所以"和老婆孩子过结婚纪念日午餐"不会被当成工作对象。
名字超过 12 字的整段会被丢弃（那是项目名不是人名）。

> 关于"没有参会人"：这**不是**记录缺陷。程序不会建议你补全参会人，报告也不会因此质疑数据质量。
> 会议识别走「参会人 + 标题」双通道，并会说明其中多少场是按标题识别的。

**设置页的结构与锚点**

- 设置页顶部有**分区目录**（按实际渲染出的区块生成），区块顺序固定为：邮箱账户 → 分析与起草策略 →
  大模型 → 日历数字人 → 定时分析与通知 → 访问与安全 → 数据去向 → 密钥存储 → 备份与恢复 →
  存储与清理 → 外观 → **运行与记录** → 关于。
- 每个区块都挂了**具名锚点**（`data-section="<区块标题>"`）。跳转写法是
  `app.navigate('settings', { anchor: '外观' })`，设置页渲染完会滚到该区块并**短暂高亮**；
  锚点用**标题**而不是序号，所以顺序调整后「返回设置」依然落在正确的卡片上。
- 「**运行与记录**」（操作台账 / 审计 + 分析运行历史）**不再占顶层导航**，
  从设置页的「运行与记录」卡片进入；该页顶部有「返回设置」，带回同名锚点。
  台账本身是 `data/audit.jsonl`，细节见 §12。

**检索预算口径（信封扫描与模型额度是两本账，别混着看）**

- **信封扫描上限** `search.envelopeScanMax`（默认 3000、最小 50）只是**封顶值**；真正生效的预算是
  `min(envelopeScanMax, max(backfillMax × 8, 600))`：默认配置（`backfillMax=40`）下为 **600 封**，
  回补额度调大时随之放大（例如 `backfillMax=100` → 800 封，但仍不超过 `envelopeScanMax`）。
- 信封扫描**只取信头**（`fetchHeaders`，每批 250 封）：**不读正文、不调模型**，所以放大它
  **不会**增加模型调用量。真正花额度的分析由 `backfillMax` 单独卡住（默认 40 封）。
- 达到上限时，返回值与界面文案会同时给出四个数并保证自洽：
  **生效上限 / 已扫描 / 未检查 / 从 IMAP 取到的 UID 总数**，
  恒有 `已扫描 + 未检查 = 取到的 UID 总数` 且 `已扫描 ≤ 生效上限`（`stats.backfill` 里分别是
  `scanLimit / scanned / unscanned / scanTotal`）。看到「信封扫描达到上限」时，
  把「检索信封扫描上限」调大，或按月分次查询。

**结论范围（结论看哪些邮件）——决定「哪 40 封」而不是「多少封」**

送进模型的**带摘录**邮件上限恒为 **40 封**（`ANALYSIS_BASIS_LIMIT`，token 额度闸门，**任何策略都不放大它**），
另有最多 40 封只给「标题 + 时间」做话题参考。原先这 40 封固定是「按时间倒序最新的 40 封」，
于是在「7 月份以来」这类跨 3 个月的查询里，第 41 封（实测 07-16）之后的邮件完全没有摘录进入结论，
而界面上看不出来。现在检索页多了「结论范围」下拉，由使用者自己决定结论的视野：

| 策略（`basis`） | 选择规则（本地确定性，无随机数） | 代价 |
| --- | --- | --- |
| `recent` 最近 40 封（默认，向后兼容） | 取当前列表顺序的前 40 条（默认按时间倒序，即最新一批） | 看得最细，但范围较宽时早期邮件进不了结论 |
| `monthly` 按月节选（每月最多 8 封） | 按 `calendar.timeZone` 的自然月分组，各组按时间倒序，**轮转取**（先每月第 1 新，再每月第 2 新……）直到 40 封或每月取满 8 封 | 覆盖整段时间（每月都有代表），但每个月的细节看得少 |
| `even` 均衡采样 | 全范围按时间倒序后，按等间隔下标 `round(i × (m-1) ÷ (n-1))` 取 n=min(40, 命中数) 个（含最早与最新各一封） | 视野最均匀，但会跳过中间月份的大部分邮件 |

- 三种策略的带摘录总数都恒为 `min(40, 命中数)`；命中不足 40 封时有多少给多少，不凑数、不重复。
- `recent` 取的是**当前列表顺序**的前 40 条（这正是它的旧语义）：默认排序是时间倒序，所以就是「最新的一批」；
  若排序是 `date_asc` / `priority`（模型按「按时间正序」「最重要的」给出的排序），取到的就不是最新的 40 封，
  此时口径会如实改写成「结论基于列表前 40 封（…）」并在 `basis.orderLabel` 里说明列表顺序——
  不允许一边取最早/最优先的 40 封、一边写「最近 40 封」。
- 选择逻辑是**本地纯函数**（`selectBasisItems`），模型不参与挑选；同一输入两次结果逐条一致，
  所以结论可复核、可解释。
- 返回值带 `basis`（与 `analysisBasis` 是**同一份口径**、同一个对象）：`{ strategy, strategyName, label, line,
  count, limit, months, rangeMonths, monthCounts, maxPerMonth, coveredFrom, coveredTo, headlines, order,
  orderLabel, excerptPartial, partial, requested, fellBack, note }`。
  `basis.line` 就是界面与提示词共用的那句话，例如
  「结论基于按月节选 24 封（覆盖 2026-07-18 ~ 2026-09-25，每月最多 8 封）」。
- 策略值非法时**回落**到 `recent` 并把原因写进 `basis.note`（界面会显示），不会静默按默认口径作答。
- 接口：`POST /api/search/emails` 的请求体加 `basis` 字段（`'recent' | 'monthly' | 'even'`，缺省即 `recent`）。

### 5.19 同一个邮箱账号的 IMAP 连接是排队用的

程序里**多个入口都会自己连同一个邮箱账号的 IMAP**：整轮分析、分析预检、检索的「按需回补」、
检索的「正文回退」、查看邮件正文/下载附件的「回源」、同步草稿到草稿箱、发送后的收尾、邮箱自检。

企业邮箱普遍限制**同一账号的并发连接数**，撞上会表现为连接被拒或账号被锁。因此现在按
**账号**（`IMAP 主机:端口:账号`）排队：同一个账号上同时只允许一条连接，**不同账号（多实例）各有各的队列，互不阻塞**。

实际表现：

| 情况 | 你会看到 |
| --- | --- |
| 另一个入口正占着邮箱 | 本次操作**排队等待**，不是失败：分析会在运行列表与顶部进度条显示「等待邮箱空闲…」，检索会有一条「已排队」的进度说明，日志里也有 `邮箱正忙：… 开始排队` |
| 等到了 | 照常继续，日志记一行排了多久 |
| 等太久 | 明确失败：`邮箱正忙：<谁在占用> 还没结束（已等待 N 秒），暂时无法开始「<操作名>」。请稍后重试。`（`code=ACCOUNT_BUSY`，HTTP 409）。**不会无限等，也不会静默丢掉这次操作** |
| 排队的人太多 | 直接拒绝（同样是 `ACCOUNT_BUSY`），而不是让队列无限增长 |
| 排队时点「取消」 | 立刻停下，不会等满超时 |

等待上限是内置常量（普通入口 30 秒、整轮分析 120 秒；同一账号最多 8 个在排队），
刻意没做成配置项——它是一个保护，不是需要你调优的参数。

想知道"现在谁占着邮箱"：`GET /api/status` 的 `mailQueue` 字段会给出
`{ busy, holder, waitedMs, queued, waiting[] }`（只有操作名与等待时长，不含账号与凭据）。

1. 复制项目文件夹，**但不要**复制 `node_modules/`、`data/`、`.env`。
2. 在新电脑上按[第 2 节](#2-一键启动推荐)双击启动。
3. 在界面里重新填邮箱、大模型（和日历）配置。

### 方案 B：连数据一起搬（保留历史分析与草稿）

1. 在旧电脑上关闭服务（关闭命令行窗口）。
2. 复制**整个文件夹**，或至少包含：

   | 需要 | 说明 |
   | --- | --- |
   | `server/`、`web/`、`test/`、`cli.js`、`start.cmd`、`package.json`、`package-lock.json` | 程序本体 |
   | `data/` | 配置、状态、简报、原文归档 |
   | `.env` | 密钥（若用环境变量方式） |

3. 新电脑上删除 `node_modules/`（依赖与平台相关，重新装更稳），再双击 `start.cmd`。
4. **注意端口**：`.env` 或 `data/config.json` 里若写死了旧机器的端口，请确认新机器该端口空闲。

> 迁移后如果日历用不了，是正常的：Google 令牌与回调地址绑定本机端口。
> 到设置页重新点「测试连接」→「开始授权」即可。

## 10. Google 日历配置详解

### 10.1 在 Google Cloud 创建 OAuth 客户端

1. 打开 <https://console.cloud.google.com/>，新建（或选择）一个项目。
2. **启用 API**：搜索 `Google Calendar API` → 启用。
   *（不做这步会报 `403 ... API has not been used in project ...`，界面会直接给出启用链接。）*
3. **配置同意屏幕**：外部 / 测试。把要用的 Google 账号加入 **测试用户（Test users）**。
   *（不加会报 `403 access_denied`。）*
4. **创建凭据** → OAuth 客户端 ID → 应用类型选 **Web 应用**。
5. **授权重定向 URI** 填（端口要与你实际使用的一致）：

   ```
   http://127.0.0.1:8787/api/calendar/oauth/callback
   ```

6. 记下 **客户端 ID** 与 **客户端密钥**。

### 10.2 填到本系统并授权

1. 设置页 → 「日历数字人（Google Calendar）」→ 填入客户端 ID、客户端密钥、重定向 URI、
   目标日历（`primary`）、时区（`Asia/Shanghai`）。
2. 点 **「保存配置」**，再点 **「测试连接」**。
3. 点 **「开始授权」**，浏览器打开 Google 授权页：
   - 因为是自建应用，会出现「此应用未经 Google 验证」的警告页；
   - **点左下角的「继续」**（不要点右侧的「返回到安全网页」）；
   - 勾选日历权限 → 继续。
4. 回到界面看到「已连接 Google 日历 · 你的账号」。

**令牌存在哪**：授权成功后拿到的 refresh token 会落盘到 `data/google-token.json`（权限 600）。
到「设置 → 密钥存储」点一次「迁入」可以把**它和邮箱授权码一起**搬进系统保管库（搬完明文文件会被删掉）。
迁移过之后**换机器/换系统账户**解不开密文，需要在日历页**重新连接一次**（这不会影响 Google 那边的任何设置）。

### 10.3 连不上 Google？配置代理（**「邮件正常、日历报错」就看着一条**）

现象：邮件收发、草稿、大模型都正常，一进「日历」页就报：

```
列出日程失败：Google Calendar 网络错误：fetch failed
```

原因通常**不是**配置写错，而是**本机到 Google 的网络出口不通**。特别注意：

> Node.js **不会**自动使用系统代理（Windows「Internet 选项」里的代理、macOS 网络偏好里的代理都不会被读取），
> 也不会读 `HTTPS_PROXY` 环境变量（那是 `curl` 之类的习惯）。
> 所以「浏览器能打开 Google，本程序却报网络错误」是非常典型的情况——
> 因为浏览器走了你的代理/VPN，而本程序在直连。

解决办法：把代理告诉本程序。

1. 打开你的代理 / VPN 软件，找到 **HTTP 代理** 端口（Clash 常见 `7890` / `7897`，v2rayN 常见 `10809`，其它软件看设置页）。
   - 只提供 SOCKS 端口时，请改用同一软件里的 HTTP 端口；本程序**不支持 SOCKS**。
   - 若是全局 TUN/虚拟网卡模式（整个系统的流量都被接管），通常可以留空——但仍建议先按下一节自检确认。
2. 打开本程序 → **设置 → 日历数字人 → 网络代理（访问 Google 用）**，填 `http://127.0.0.1:7890`（换成你的端口），点 **保存配置**。
   也可以在 `.env` 里写 `MAILBOT_GOOGLE_PROXY=http://127.0.0.1:7890`（改完要重启服务）。
3. 回到设置页点 **「测试连接」**，或执行 `node cli.js doctor --deep`，看自检里的 **「Google 网络出口」** 一项：

   | 自检结果 | 含义 |
   | --- | --- |
   | ✅ 可达（xxx ms，经代理 http://…） | 通了 |
   | ❌ 连接超时（ETIMEDOUT） | 本机到 Google 没有可用出口 → 配代理 |
   | ❌ 连接被重置（ECONNRESET） | 连接被网络中间设备阻断 → 配代理 |
   | ❌ DNS 解析失败（ENOTFOUND） | 本机 DNS 找不到 Google 域名 → 换 DNS 或配代理 |
   | ❌ 连接被拒绝（ECONNREFUSED） | 代理端口没人监听 → 代理软件没开或端口填错 |
   | ❌ 代理要求身份验证（407） | 代理需要账号 → 写成 `http://用户名:密码@主机:端口` |

> 代理设置**只作用于 Google**（日历与 Google 授权）。收发邮件、大模型调用走原网络，不受影响——
> 这也是为什么可以在「邮件正常」的前提下单独给日历配代理。

### 10.4 日历使用要点

| 操作 | 说明 |
| --- | --- |
| 对话建日程 | 日历页输入如「明天下午 3 点和张总开周会，会议室 A，1 小时」→ 生成待确认草稿 → 确认后写入 |
| 从邮件生成日程 | 点「扫描最近 24 小时邮件」→ 给出时间建议 → 逐条确认写入，日程描述里带来源邮件。这个面板就在**「对话建日程」下面**（两个"产生日程"的入口在同一栏，不用滚到页面底部） |
| 写入前修改 | 每条建议有「**编辑后写入**」：弹窗可改**主题 / 全天或起止时间 / 地点 / 说明**，改完再写入；建议已准确时可用「直接写入」跳过。邮件里抽出来的时间常常"差一点"，所以确认这步不走过场 |
| 查看安排 | 今日 / 明日 / 最近 7 天的统计、冲突提示与文字分析 |
| 刷新 | 页面**不会**在切换标签时自动刷新；要更新请点「刷新日历」 |

> **扫描窗口真的只有 24 小时**：按**邮件日期**过滤（不是"库里最新的若干封"）。
> 面板右上角显示本次窗口起点，便于核对。
>
> **窗口内没有已分析的邮件时会自动补一次分析**：程序先跑一遍「分析最近 24 小时邮件」
> （跳过已分析邮件，不重复花 token），再提取日程。所以第一次点可能要等十几秒；
> 完成后界面会说明"已自动分析：拉取 N 封、新分析 M 封"。若自动分析失败（例如邮箱连不上），
> 会如实给出原因，接口本身仍然可用（只是没有建议）。

> **写操作不重试**：创建日程若因网络问题重试会产生重复日程，因此只执行一次；
> 失败时如实报错，由你决定是否重试。

## 11. 常见问题排查

### 邮箱

| 现象 | 原因与解决 |
| --- | --- |
| `535 authentication failed, system busy` | ①**SMTP 主机写错**（最常见）：确认是服务商给的 SMTP 地址，不要照抄 IMAP 的；②认证方式：把「SMTP 认证方式」改成 `LOGIN`；③授权码失效：重新生成客户端专用密码 |
| `No password configured` | 授权码没保存。填完后要点该段的「保存配置」 |
| IMAP 登录失败 | 端口/加密不匹配：993 配 SSL(true)，143 配 STARTTLS/明文(false)。部分企业邮箱要求先开启 IMAP 服务 |
| 收不到最近邮件 | 确认「扫描文件夹」正确（默认 `INBOX`）；确认回看窗口够大。若怀疑漏信，跑 `node cli.js doctor --deep` 看「近 N 小时邮件量」并与邮件客户端核对数量——整条链路已改为拉头部（不再依赖会静默丢包的 `ENVELOPE`），正常情况下应当数量一致 |
| 分析结果里某封邮件主题显示「(无主题)」或时间为「—」 | 早期版本的显示缺陷，现已归一化并加了兜底。若仍出现，说明这封邮件的头部确实没有主题/时间，行内会给出 `文件夹 #UID` 便于定位 |
| 检索查不到某些邮件 | 检索默认回看 30 天，**最长 366 天（约 1 年）**；超出时不会静默改小，结果里会写明「你要的起始日期超出上限，已按 X 起检索」。若这批邮件从未被分析过，系统会自动「按需回补」拉取 |
| 命中列表比预期少 | 命中列表默认就会列出范围内**全部**命中（最多 1000 条），不再受模型给的条数限制。若看到「命中 N 封 / 已列出前 M 封」，说明命中数超过了单次展示上限：缩小时间范围或加上发件人/主题条件后分次查询。若看到「信封扫描达到上限……还有邮件未检查到」，把「检索信封扫描上限」调大或按月分次查询 |
| 命中列表里有些条目标着「仅信封·未分析」 | 这是正常的：这些邮件只按发件人/时间/主题对上了，没有花模型额度分析，因此没有摘要与分类。摘要只属于带摘录的那一批（上限 40 封，策略由「结论范围」下拉决定），界面会写明「结论基于……（覆盖 A ~ B）」 |
| 结论里提到的邮件明显偏向最近一段时间 | 结论范围选的是**最近 40 封**（默认）。宽范围查询（如「7 月份以来」）会因此看不到早期邮件：改选「按月节选」或「均衡采样」后**重新检索**，结论视野就会覆盖整段时间（带摘录上限仍是 40 封，不会多花额度） |
| 「结论范围」下拉改了但没生效 | 改选只改策略，不会自动重跑（否则会悄悄多花一次模型额度）。界面会提示「已改动」，点「检索并分析」后生效 |
| 日期看起来差一天 | 时区问题。把设置里的时区设为你的实际时区（如 `Asia/Shanghai`），系统按它判断「哪一天」 |
| `邮箱正忙：… 还没结束（已等待 N 秒），暂时无法开始「…」` / `code=ACCOUNT_BUSY` | 同一个账号上另一个入口（分析 / 检索回补 / 正文回源 / 草稿同步 / 自检）还占着 IMAP 连接，排队到超时了。**这不是故障**：等它跑完再点一次即可；`GET /api/status` 的 `mailQueue.holder` 会告诉你是谁在占用。详见「5.19 同一个邮箱账号的 IMAP 连接是排队用的」 |

### 大模型

| 现象 | 原因与解决 |
| --- | --- |
| `大模型未配置完成（缺少 API Key）` | 到设置页填 Key 并**保存** |
| `大模型鉴权失败（HTTP 401）` | Key 错误或余额不足 |
| 分析很慢 / 花费高 | 调小「单次最多处理邮件数」与「单次最多起草数」，或调小「正文送模型字符上限」 |
| 分类结果偶尔降级 | 模型返回非法 JSON 时会自动重试并降级为保守结论，日志里会记录，不影响整体运行 |

### 日历

| 现象 | 原因与解决 |
| --- | --- |
| `列出日程失败：… fetch failed` / 各种网络错误 | **本机到 Google 的出口不通**，不是配置错。见 [10.3 配置代理](#103-连不上-google配置代理邮件正常日历报错就看着一条) |
| `Google Calendar API 尚未启用` | 界面会给出启用链接，点开后启用 API，等 1-2 分钟重试 |
| `access_denied` | 你的 Google 账号不在「测试用户」列表里，去 OAuth 同意屏幕添加 |
| **`Token has been expired or revoked`／「授权已失效，需要重新连接」** | **不是配置错，代理与 OAuth 凭据都不用动**。同意屏幕处于「测试」发布状态时，Google 只给 refresh token **7 天**寿命，到期必须重新授权。到「日历」页点「**重新连接 Google 日历**」即可恢复。**想免去这个 7 天周期**：Google Cloud →「OAuth 同意屏幕」→ 发布状态改为「**已发布**」，然后重新授权一次以取得长效令牌。个人自用不必通过验证，授权时会看到"未验证应用"提示，点「继续」即可 |
| `redirect_uri_mismatch` | Google Cloud 里登记的「授权重定向 URI」与设置页里的不完全一致（端口也要一致） |
| 「此应用未经 Google 验证」 | 自建应用的正常提示，点左下角「继续」即可 |
| 写入失败无提示 | 界面会弹出错误原文；创建日程失败不会自动重试，避免产生重复日程 |
| 日程时间差 8 小时 | 时区配置不对，检查 `calendar.timeZone` |
| 改代理后仍不通 | ①改的是 `.env` 但没重启服务；②代理软件只开了 SOCKS 端口；③代理软件本身没连上节点 |
| **配了代理、日志显示隧道已建立，却仍 ECONNRESET / 超时** | **旧版本的代码 bug，现已修复**：代理路径里写了 `agent: false`。Node 在 `agent: false` 时会新建一个一次性 Agent 并**忽略 `createConnection`**，于是刚建好的 CONNECT 隧道 socket 被丢弃，程序自己去直连 Google —— 在国内就是 ECONNRESET 或超时。现在已去掉该行（`server/lib/http.js` 里有注释说明，别再把它加回来）。若你从旧版本升级，**重启服务**即可生效 |
| 生成的日程时间总是 17:00→17:05 这种 5 分钟 | 邮件里抽到的是"时间点"而不是日程。现在会自动规整：开始对齐到**整点/半点**（截止类向下取整，保证提醒不晚于邮件里说的时间），时长不足 30 分钟的补成 30 分钟；卡片上会标注"时间已规整"，仍可在写入前修改 |
| **Foxmail 里已发送邮件时间早 8 小时** | 旧版本用 `toUTCString()` 写了 `… GMT`，客户端按原样显示就是 UTC。现在 `Date` 头按 `calendar.timeZone` 写成 `+0800`（如 `Thu, 01 Oct 2026 11:41:49 +0800`）；**若仍显示 UTC，先把客户端时区设为 (UTC+08:00) 北京**，并确认服务已重启（旧版本生成的邮件不会追溯修改） |
| 界面时间与自己电脑不一致 | 界面按「设置 → 日历时区」渲染，而不是浏览器时区；要跟随本机就把该项改成自己的时区 |
| **简报说「共 11 封」而卡片显示 5 封** | 两个口径不同的数字，现已统一并会在界面说明：①**拉取**用 IMAP `SEARCH SINCE`，它只精确到"天"，所以会多带回当天更早的邮件 → 现在拉取后会**按精确时刻再滤一道**，"拉取数 = 窗口内数 = 卡片数"；②简报是**那次分析时的快照**，卡片是**打开页面时实时重算**的，旧邮件会随时间滑出窗口 → 两者不同时总结区会写明"简报写于 X，当时 N 封；现在同一窗口 M 封——数字不同是因为时间在走" |
| **简报说「N 封高优先级需尽快处理」，卡片却是 0** | 卡片数的是「**需要你回信**」的邮件（`needsReply` + 高优先级 + 直接发我）；会议通知、到期提醒不需要回复，所以不进那份清单——它们现在归入**独立的「需留意」一栏**。提示词也已收紧：统计数字必须原样引用，需回复为 0 时那一节只能写「无」 |
| 「需留意」一栏是空的 | 该栏依赖逐封分类里的 `worthNoting` 字段，而**旧的分析记录没有这个字段**（一律按"不进"处理，行为可预测）。**重新分析一次**即可补齐——引擎每轮都会重新分析窗口内的邮件，不需要清数据 |
| 分析 7 天/30 天时提示「有邮件超出取信上限未分析」 | 这是如实告知：单次取信有上限（24h→60、3天→180、7天→420、30天→1800，硬顶 2000）。缩短时间段分次分析即可，已分析过的邮件不会重复消耗 |
| 「继续分析新邮件」跑完看不到新草稿 | 旧版本只重绘不重新取数，需要手动刷新页面；现已修复（跑完自动刷新列表并提示新增封数） |
| 切到「最近 7 天」但总结还是 24 小时的内容 | 旧版本会拿最近一次简报冒充本期。现在总结只反映当前窗口，并用一行小字说明上次简报属于哪个窗口；点一次「分析最近 7 天」即可生成该窗口的 AI 总结 |
| 找不到「刷新」按钮 | 已按需求移除。数据变更（含定时任务跑完的 SSE 事件）会自动让页面重新取数；换时间范围也会自动重取 |
| 弹窗背后没有变暗（尤其深色/绿色主题） | 旧版本遮罩写死且过浅，深色页面上几乎看不见。现在用主题变量 `--scrim`（深色 0.68 / 绿色 0.72）+ 背景模糊，并锁住页面滚动 |

## 12. 备份、清理与安全

### 备份

```bash
# 只备份配置与状态（不含原文归档，体积小）
copy data\config.json  backup\
copy data\state.json   backup\
copy .env              backup\
```

`data/raw/` 是邮件原文归档、`data/reports/` 是简报，可直接删除以释放空间
（不会影响配置与草稿；再次分析时会重新拉取）。

`data/attachments/` 是**待发附件**：发送成功后内容会自动清理，删除草稿时文件一并删除，
所以正常情况下它几乎是空的。如果里面还有文件，说明有草稿还没发出去——删掉对应草稿即可。
（收到的附件不在这个目录，它们在 `data/raw/*.eml` 里，跟着原文归档一起管理。）

`data/audit.jsonl` 是**操作台账**：记录"改了外部系统"的写操作（创建/删除日程、发送邮件、
同步草稿、删除草稿）。它**只追加、不改写、永久保留**，所以会随时间增长——但每条只有一个 JSON 对象、
体积很小（一次批量建 22 条日程约几 KB）。要清理可直接删除该文件，**不影响任何功能**
（只是历史台账没了）。用 `grep`、Excel 或任何文本工具都能直接查看。

> 界面入口是「**设置 → 运行与记录**」卡片（该页不再占顶层导航）。那里可按类别/动作/关键词/只看失败筛选，
> 并「下载 JSONL」；同页还有**分析运行历史**（最近 30 次）。页顶「返回设置」会滚回设置页的那张卡片。

#### 台账里没有以前的操作，怎么办

台账是**功能上线之后**才开始记的。点页面上的「**补录历史**」可以回填，程序从两个来源取：

1. **本地日历会话记录**——「对话建日程」创建的日程，会话里留有「已写入日历：标题　时间」；
2. **Google 事件上的来源标记**——「从邮件生成」创建的事件带 `mailbotSource` / `mailbotRef`。

补录**只读 Google、只追加本地文件**，不会新建或改动任何日程；已补过的按（标题+时间）或日程 id 去重，
可重复点。记录时间用当时的创建时间，时间线不会串。

**顺序上先本地、后 Google**：本地会话记录**不需要网络**，一瞬间就补完；Google 那一路只是补充。
所以即使访问 Google 不通（没配代理/代理没开），点补录也会**立刻**把本地那批补回来，
并提示"Google 日历这一路未成功：<原因>"——不会出现"点了没反应、一直转圈"。
若真的提示超时，先确认总览页能否正常分析邮件（那条链路也走 Google 的话会一起暴露问题）。

> 旧版本是**先查 Google 再补本地**，于是一旦网络卡住，整件事被拖死几分钟且毫无反馈（用户实测）。现已调整顺序并加了超时上限（服务端 20 秒 / 前端 40 秒兜底）。

> 旧版本的「对话建日程」不给事件打来源标记，所以在 Google 上认不出程序建的日程
> （实测 107 条里只有 3 条带标记）。现已修复：这条路径也会写入 `mailbotSource=chat`。

> 台账为空时「下载 JSONL」是禁用的——旧实现返回 200 + 空 body，浏览器会下载一个
> **0 字节文件**，打开是空的，看起来像功能坏了。

### 安全须知

| 项 | 建议 |
| --- | --- |
| 监听地址 | 默认 `127.0.0.1`，只有本机能访问。**不要**改成 `0.0.0.0` 除非你清楚风险 |
| 访问令牌 | 在共享电脑或需要局域网访问时，设置 `MAILBOT_WEB_TOKEN`，并使用带 `?token=` 的地址 |
| 密钥 | 优先放在 `.env`（不进版本库）。`data/config.json` 若含密钥，注意不要外发 |
| 发送策略 | 保持 `confirm`。`auto` 只影响是否允许批量发送接口，界面仍会二次确认 |
| 数据 | 全流程数据只保存在本机；除邮箱/大模型/Google 之外不会外发任何内容 |
| 权限 | 应用只读扫描信箱（EXAMINE），不会把你的邮件标记成已读或删除 |

### 13.1 偶发的 `fetch failed` / `bad port`：根因与排查指引

**曾经的现象**（2026-10 定性并修复）：连续跑套件时，约每 10~30 次会红一次，报错只有一句
`网络错误：fetch failed`，偶尔能带出 `← Error bad port`，而且**每次红的用例都不一样**
（登录限速 / 日历回顾 / HTTPS 各出现过）。判定一个字都没放宽，所以只能当"环境抖动"忍着。

**根因**：`fetch`（浏览器与 Node 的 undici 都遵守同一个规范）有一份**禁用端口名单**
（"bad port"：`0/1/7/…/6000/6665-6669/6679/6697/10080` 共 83 个）。指向这些端口的请求
**在建立连接之前就被拒**，因此报错既不含 URL 也不含原因。而测试与程序里的本地服务用的是
`listen(0)`——端口由操作系统的**动态端口范围**分配。两者一旦相交，落到那个端口上的服务
**永远无法被 fetch 访问**，红在哪条用例上纯看运气。

本机实测（Windows，`netsh int ipv4 show dynamicport tcp` = 起始 1024 / 13977 个，
即 **1025–15000**）：

| 检查 | 结果 |
| --- | --- |
| 动态范围与禁用名单的交集 | 19 个：`1719 1720 1723 2049 3659 4045 4190 5060 5061 6000 6566 6665 6666 6667 6668 6669 6679 6697 10080` |
| 裸 `listen(0)` 抽 2 万次 | 命中 20 次（≈1/1000；早期 6000 次测到 1/600） |
| 一次日历自检起的临时端口 | 约 23 个 → 每套约 1/30 会踩到 |
| 修复前本机连跑 60 次 | **红 3 次**，全部是 `TypeError: fetch failed ← Error bad port` |
| 修复后连跑 60 次 | 红 0 次 |

> 名单是**逐个端口与 undici 实测核对**出来的，不是照抄文档：把 1025–15000 全扫一遍、
> 只认 `cause: bad port` 这一种失败，结果正是"漏了 6679、其余全对"（见下面的扫描命令）。

**修复**（不是加重试，也不放宽断言）：

1. `test/lib/port.js` 的 `listenRandom()` 与 `server/index.js` 的 `startServer({port:0})`
   在拿到系统分配的端口后**检查是否落在禁用名单**，是则关掉重抽（连续 8 次都中会明确报错，
   不会把坏地址交出去）；用户**显式指定**的端口一律照办，不静默替换。
2. 名单与判定只实现一处（`server/lib/http.js` 的 `FORBIDDEN_FETCH_PORTS` /
   `isForbiddenFetchPort`），测试与生产共用；`test/selftest.js` 里有一条用例**逐个端口**
   与 undici 的真实行为核对，Node 侧名单一变就会红。
3. 所有 HTTP 失败现在都带**确切 URL + 完整 `error.cause` 链**（`server/lib/http.js` 的
   `requestFailureDetail` / `decorateRequestFailure`，大模型客户端 `LlmClient` 也接上），
   测试侧再由 `test/lib/http.js` 的 fetch 诊断层补上 URL——所以**下次再红，日志自己会说明白**。

**再遇到时的排查顺序**（照抄即可）：

```powershell
netsh int ipv4 show dynamicport tcp           # Windows：动态端口范围
netsh int ipv4 show excludedportrange protocol=tcp
# Linux/macOS：
sysctl net.ipv4.ip_local_port_range
```

把动态范围与上面那份名单对一下：

- **有交集** → 已经不是"抖动"，而是这个确定的机制。跑 `node test/selftest.js`，
  其中「测试端口：listen(0) 不得交出 fetch/浏览器的禁用端口」会直接告诉你是哪一环；
  也可以跑大模型服务的自检页，看失败信息里 `requestUrl` 的端口是不是禁用端口。
- **无交集**（例如默认的 49152–65535）→ 那这次的 `fetch failed` 是另一回事，
  直接读失败信息里的 `诊断={...}`：`requestUrl` 是打哪个地址，`errorChain` 是底层原因
  （`ECONNREFUSED` / `socket hang up` / 证书……），不要再从"是不是端口"猜起。

如果怀疑**名单本身**与当前 Node/undici 不一致（升级 Node 后值得跑一次）：

```bash
node test/tools/scan-bad-ports.mjs              # 全量 1–65535，约 30 秒
node test/tools/scan-bad-ports.mjs 1025 15000   # 只扫本机动态端口范围，更快
```

它把端口逐个发给 undici、只认 `cause: bad port` 这一种失败，输出"名单缺失/多余"两个清单
（有缺失时退出码为 1）。`6679` 就是这么发现的：初版名单是照记忆写的，漏了它。

> **对使用者的实际影响**：如果你把本机模型（Ollama / LM Studio）或代理填在
> `6000`、`6667`、`10080` 这类端口上，程序与浏览器都会直接拒连（规范如此），
> 报错为 `网络错误：fetch failed`。换个端口即可——现在错误信息里会点名"该端口被列为禁用端口"。
>
> **CI 观察**：本机（Windows 动态范围被改成 1025–15000 的机器）已定性并复现
> （修复前 3/60 红、修复后 0/60）。**默认动态范围**（49152–65535）的机器与
> Linux/macOS 上碰不到这一档，所以这条修复在那些平台上体现为"没有变化"。
> 历史上 `ubuntu/20` 那次红与本次是**不是**同一原因，尚无证据，仍需 CI 观察
> （见 `docs/决策索引.md` 的"教训清单"）。
